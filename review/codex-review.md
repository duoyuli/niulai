# 架构评审：当前全仓存量代码

评审日期：2026-10-23。

确认 **7 项架构问题：3 项高、4 项中**。主要风险不是目录划分混乱，而是后台流程、事务和缓存的责任边界不完整：静态依赖没有环，但部分一致性仍依赖调用顺序和人工约定。

以下均以评审时的 `main`、HEAD `a63ebec` 为依据。评审阶段没有修改代码或文档；本文件随后按用户要求归档。

## 发现

### 1. [高] 同步完成事件混用了「任务结束」和「后处理完成」两种状态

- **原则：** 显式状态转换、错误处理边界。
- **位置：** `backend/src/sync/run.rs:109`、`backend/src/sync/executor.rs:393`、`backend/src/bootstrap.rs:62`、`backend/src/sync/run.rs:228`。
- **现象：** 运行转为终态时就写入 `sync_event_pending`，此时复权后处理还没有完成；重放直接进入建议刷新，不先补齐后处理。另外，批量重放只取最后一个 `run_id` 检查涨跌停池变化，却清除此前所有运行的待处理标记。
- **代价：** 在任务结束、复权完成之间重启，应用层可能先基于旧复权结果生成建议。多个事件积压时，如果较早运行更新了涨跌停池、最后一个运行没有相关变化，较早的变化可能被确认掉，却没有更新缓存版本。以后增加新的后处理消费者，还要继续依赖这些隐含时序。
- **建议：** 分开持久化「待后处理」「可供应用消费」「消费完成」。合并事件时汇总本批全部运行的影响，只确认实际处理的事件，不按 `run_id <= 最大值` 整段清除。成本中等，应优先补重启和乱序完成测试，不需要引入外部消息队列。

### 2. [高] 建议后台重算没有可恢复的作业边界

- **原则：** 副作用生命周期管理、错误不得被误判为成功。
- **位置：** `backend/src/api/accounts.rs:320`、`backend/src/advice/mod.rs:196`、`backend/src/advice/mod.rs:257`、`backend/src/advice/mod.rs:291`。
- **现象：** 账户修改提交后，由 API 另行调用 `regenerate_soon`；待重算状态只保存在进程内 `HashMap`，任务通过未纳入组件监督的 `tokio::spawn` 执行。失败只写日志，然后移除状态。批量刷新同样吞掉单个账户的生成错误并返回成功，而维护任务只检查「是否已有当天建议」。
- **代价：** 保存持仓或规则成功后，若重算失败或进程退出，旧建议仍然存在，因此维护任务不会把它当成待修复项。页面也可能从「更新中」恢复为普通状态，却仍展示旧结果。新增账户写入口时，还必须记得额外调用重算函数。
- **建议：** 在账户修改事务内写入待重算标记或目标版本，由受监督的消费者执行；成功保存匹配版本的建议后再确认，失败保留重试状态。批量刷新应返回失败账户，不能让事件层误确认。成本中等，不建议继续增加纯内存补丁。

### 3. [高] 建议执行、处理状态和影子订单没有统一的事务所有者

- **原则：** 信息隐藏、业务不变量的单一所有者。
- **位置：** `backend/src/account/mod.rs:578`、`backend/src/api/accounts.rs:702`、`backend/src/api/accounts.rs:739`、`backend/src/api/accounts.rs:771`。
- **现象：** `account::record_advice` 在一个事务内提交流水、持仓、现金和建议执行状态；随后 HTTP handler 再单独更新 `app.shadow_order`。跳过建议也分两次写入；撤销「不做」只删除处理状态，没有恢复影子订单的 `cancelled` 状态。
- **代价：** 第二次写入失败时，账已经记成功，影子订单却仍显示未成交；重试又会被「已经记过」拦截。撤销「不做」则存在明确的两份状态不一致。以后增加部分成交、撤销或新调用入口，必须同时理解 API、账户和建议三个模块的内部表。
- **建议：** 建立一个应用层的建议处理入口，统一编排执行、跳过、撤销；各模块提供必要的事务内操作，流水、处理状态和影子订单原子提交。无需让 `account` 反向依赖整个 `advice` 模块。成本小到中，应优先处理。

### 4. [中] 研究运行缺少完整、可持久化的配置模型

- **原则：** 单一事实来源、接口与应用逻辑分离。
- **位置：** `backend/src/api/research.rs:175`、`backend/src/api/research.rs:189`、`backend/src/api/research.rs:280`、`backend/src/api/research.rs:536`。
- **现象：** HTTP 层同时负责组装研究配置、计算哈希、统计历史试验和保存结果。`FactorConfig` 不含检验的 `quantiles`、组合的本金与成本参数；数据库只保存哈希、manifest 和摘要，没有保存完整配置本身。
- **代价：** 改变分组数、本金或成本，会改变结果，但不会形成新的配置哈希。离开当次 HTTP 响应后，也无法仅凭运行记录完整还原参数。以后增加 CLI、批量实验或重跑功能，容易再复制一套配置与统计逻辑。
- **建议：** 提取类型化的研究运行配置，由它派生计算参数、配置哈希和持久化内容；区分「方法定义」与「一次具体运行」，明确哪些参数参与试验去重。HTTP 层只做输入适配。成本中等，宜在增加下一种研究参数或批量入口前完成。

### 5. [中] 全市场计算的并发限制放在扫描函数内，没有覆盖整个任务

- **原则：** 资源生命周期与应用用例边界一致。
- **位置：** `backend/src/analysis/prices.rs:315`、`backend/src/analysis/factor_lab.rs:129`、`backend/src/analysis/factor_lab.rs:220`、`backend/src/api/research.rs:521`。
- **现象：** 信号量仅在 `for_each_table` 内持有。财报和行业数据在取得槽位前加载；扫描返回后槽位释放，面板的 `finish`、横截面检验和组合模拟仍继续运行。
- **代价：** 「最多两个扫描」并不等于「最多两个完整研究任务」。排队请求可以先加载财报，完成扫描的请求可以继续持有大面板并计算，同时让后面的请求开始扫描。增加用户或延长区间时，实际内存和 CPU 峰值不能由当前限制保证。
- **建议：** 把预算控制提升到完整研究用例：从加载输入到计算结束都持有许可，保留前台与后台的独立预算；底层扫描只负责分批读取。成本中等，可暂缓进程拆分，但在提高并发前应先修正限制范围。此次未做压力测试，不据此断言已经发生 OOM。

### 6. [中] 因子排名的缓存失效没有覆盖实际输入依赖

- **原则：** 派生数据的单一事实来源、显式依赖。
- **位置：** `backend/src/advice/ranking.rs:36`、`backend/src/analysis/factor_lab.rs:129`、`backend/src/bootstrap.rs:48`、`backend/src/advice/mod.rs:250`。
- **现象：** 排名缓存键只有交易日和因子配置，没有数据版本或 TTL。排名实际依赖行情、财报和行业成分；但同步完成后，只有价格或涨跌停池变化才触发 `refresh_all(true)` 并清缓存。财报或行业成分单独更新不会进入这条路径。
- **代价：** 同一交易日补齐或修订财报后，账户仍可能使用旧排名；手动重新生成建议也可能命中旧缓存。当前默认组合已经使用财务因子，这不是为未来需求预留的抽象问题。
- **建议：** 为因子输入维护明确的数据版本，把相关版本纳入缓存键；应用编排层根据变化的数据集更新版本。无需让通用同步框架理解因子公式。成本小到中，宜与第 1 项一起处理，但两者分别解决事件确认和依赖覆盖问题。

### 7. [中] 前端账户变更的缓存失效规则仍散落在多个组件中

- **原则：** DRY、共同闭包原则。
- **位置：** `frontend/src/lib/queryInvalidation.ts:14`、`frontend/src/components/PositionsEditor.tsx:59`、`frontend/src/components/AdviceView.tsx:393`、`frontend/src/main.tsx:12`。
- **现象：** 已有统一的 `invalidateAccountQueries`，但校准持仓和执行建议仍各自维护刷新清单。校准没有刷新流水查询，执行建议没有刷新净值、建议回看等查询；全局查询默认在 60 秒内视为新鲜。
- **代价：** 先看记录，再校准持仓或执行建议，立即返回记录页时，部分查询可能继续显示旧缓存。以后新增账户派生视图，需要逐个找 mutation 回调补登记，容易漏改。
- **建议：** 统一使用账户域的缓存更新函数，明确区分「账本变化」「建议状态变化」「设置变化」的影响范围，补充缓存失效测试。保留生成客户端不动，不需要新增全局状态框架。成本小，可作为独立收尾项。

## 结论

当前模块化单体的方向合理，**不需要通过拆微服务、多 crate 或全面引入仓储 trait 来解决这些问题**。最值得先做的是统一同步事件的阶段、建议重算的恢复机制，以及建议处理的事务边界。

优先顺序建议为：**1～3 → 4～6 → 7**。这比按大文件行数机械拆分更能降低下一次变更的成本。

## 结构概览

- `server` / CLI 负责启动，`bootstrap` 负责应用事件编排，`api` 提供接口。
- `advice → account / analysis` 的主依赖方向清楚，`analysis` 不反向依赖账户。
- `sync → vendor` 负责配置驱动的采集、队列和投影；PostgreSQL 同时承担状态持久化。
- 前端总体保持 `pages → components / hooks → lib / api`，没有发现页面间反向引用形成的环。
- 当前主要缺口位于这些模块之间的事务、恢复与失效协议，而不是目录结构本身。

## 值得保持的结构

- **纯计算核心已经存在。** 建议生成、因子检验和组合模拟可以直接使用普通数据测试，不应为了重构重新混入 I/O。见 `backend/src/advice/generate.rs:251`、`backend/src/analysis/factor_lab.rs:807`。
- **同步写入边界较完整。** 租约确认后，raw、类型化投影和游标在同一事务内写入。见 `backend/src/sync/executor.rs:331`。
- **同步与账户之间没有直接调用依赖。** 应用事件层的方向值得保留，需完善的是可靠性协议，而不是退回同步执行器直接调用建议模块。
- **API 契约有生成和漂移检查。** 路由与 OpenAPI 同源，前端客户端生成，CI 检查漂移；不建议再维护一套手写接口类型。见 `backend/src/api/mod.rs:148`、`.github/workflows/ci.yml`。
