# Rust 适配

本文说明通用原则在 Rust 中的落地方式，并融合 [Google Rust 风格指南](https://google.github.io/styleguide/rustguide.html) 中与结构相关的规则。Google 指南本身以 [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/) 和官方风格指南为基础，只在冲突处覆盖。

## 先区分库代码和应用代码

Google 指南把 API 设计规则分成两种力度：库代码（给其他项目用、解决通用问题）必须遵守；应用代码（只服务一个应用、解决具体问题）作为强烈建议，优先简单直接，避免过早泛化。

评审时先判断被评审的代码属于哪一类。单个应用仓库中的绝大部分模块是应用代码：不要求 `impl Into<T>` 参数、返回迭代器、`#[non_exhaustive]` 这类面向外部使用者的灵活性；用这些要求去评审应用代码会制造过度设计。

## 不适用的规则

Google 指南中标注 `[chrome]`、`[Fuchsia]` 的条目只适用于对应代码库，不作为通用评审标准：「每个 crate 一个文件」「源文件扁平、不分子目录」「不使用 `async`/`.await`」「不直接创建线程」「使用指定的 mutex 和导入宏」。Cargo 项目使用常规目录结构，Tokio 等异步运行时是正常选择。

纯格式规则（rustfmt 配置、导入的分组粒度、类型名是否限定）属于代码风格，架构评审不展开。评审 diff 时如有明显问题可以在「低」级别顺带提及，以项目已配置的 rustfmt 和 clippy 为准。

## 组件与模块边界

### 组件的单位

- Rust 的可见性边界是模块，编译和发布边界是 crate。单 crate 应用中，「组件」对应 `src/` 下的顶层模块。`scripts/dep_graph.py --lang rust` 按顶层模块统计依赖。
- crate 内部的模块环不会导致编译失败，因此依赖环在 Rust 中尤其容易悄悄出现。顶层模块之间的环按 ADP 报告。
- 当顶层模块之间需要强制隔离（禁止反向依赖、并行编译、独立测试）时，可以拆成 workspace 中的多个 crate，让编译器强制依赖方向。这是重量级手段，只在边界已经稳定、并且反复被破坏时建议。

### 可见性就是信息隐藏

- 默认私有，按需放宽：`pub(super)`、`pub(crate)`、`pub`。单 crate 应用中出现大量 `pub` 不一定是问题，但如果某个模块的内部辅助函数被其他顶层模块直接调用，说明边界在泄漏。
- 检查方法：对一个顶层模块，搜索其他模块对它的引用（`crate::<模块>::`），列出实际被使用的项，判断它们是否构成一个清晰的对外接口。
- 结构体字段公开意味着结构体的表示成为了接口的一部分。领域对象的字段公开并被多个模块直接修改时，不变量就无法由类型保证。

### 模块组织（来自 Google 指南）

- **非叶子模块只做声明和重新导出**：`mod.rs` 或父模块文件应主要包含 `mod` 声明和 `pub use`，具体实现放在叶子模块中；允许少量「把各部分串起来」的核心代码。父模块中堆积大量实现会混淆结构和内容，也让对外接口难以辨认。
- **按主要条目命名文件**：叶子模块以其主要类型或主题命名（`Foo` 放在 `foo.rs`），让文件用途一目了然。
- **父模块重新导出公共 API**：让子模块保持为实现细节，外部通过父模块访问。外部代码深入引用 `crate::a::b::c::Item` 这类深路径，往往说明父模块没有提供清晰的接口。
- **不使用 glob 导入**：`use foo::*` 隐藏了依赖来源，除了 `use super::*`（测试模块中）和父模块的 `pub use submodule::*` 等例外。跨顶层模块的 glob 导入会让依赖图难以追踪。

## SOLID 在 Rust 中

### SRP

- 单位是模块和结构体及其 `impl` 块。一个 `impl` 块的方法可以按字段子集清楚地分组时，考虑拆分结构体。
- 「巨型文件」在 Rust 中常见于 HTTP 处理函数集合和数据访问模块。判断标准仍是变化原因，而不是行数。

### OCP

- 枚举加穷尽 `match` 是 Rust 中最常用、通常也是最好的扩展方式：新增变体时编译器会指出所有需要处理的位置。不要因为存在 `match` 就建议改成 trait。
- 只有当同一个分派在多处重复、并且扩展维度确实频繁变化时，才考虑 trait 加实现，或者把分派集中到一处（一个返回行为描述的函数、一张注册表）。
- 避免在 `match` 中使用通配分支 `_ =>` 吞掉未来新增的变体，除非确实意图如此；通配分支会让编译器无法提醒遗漏。

### LSP

- 体现为 trait 的约定。检查每个实现是否满足 trait 文档描述的语义；`unimplemented!()`、`todo!()`、`panic!("not supported")` 出现在 trait 实现中是强信号。

### ISP

- 小 trait 优先。把只被部分实现者使用的方法拆到独立的 trait。
- 函数参数接收整个应用状态（例如 Web 框架的 `State<AppState>`）应止于入口层；向内部业务函数传递真正需要的部分（连接池、配置的某个字段），让业务函数的依赖一目了然。

### DIP

- 抽象通过 trait 表达；但按照 Google 指南，**只在需要时定义 trait**：需要泛型约束 `T: Trait`、需要接收或返回 `impl Trait` 或 `dyn Trait`、或定义扩展 trait。不要为了组织代码或「也许将来要换实现」而定义 trait。
- 在 Rust 应用中，实现依赖倒置的更轻量方式常常是：把纯计算提取成接收普通数据的函数，由外层负责 I/O 后传入数据；底层需要通知高层时，用通道（channel）、回调闭包或事件枚举，而不是直接调用高层模块。
- 泛型与 `dyn Trait` 的选择：库代码优先泛型（静态分发、可内联，并且有些 trait 不是 dyn 兼容的）；代码体积或异构集合重要时用 `dyn`。应用代码中二者都可以，选择更简单的那个。

## 类型设计（来自 Google 指南）

- **新类型（newtype）与类型别名**：语义不同、需要独立 API、可能更换底层类型、或者值容易混淆（例如不同含义的 ID、日期、金额）时用新类型，让编译器防止混用。类型别名不提供任何保护。跨模块传递容易混淆的同类型原始值（多个 `i64` ID、多个 `f64` 价格）是值得报告的结构问题。
- **用枚举代替布尔参数**：布尔参数含义不明显时（`refresh(pool, true)`），用枚举表达意图；保留布尔时加注释说明。跨模块边界的布尔参数尤其值得关注，因为调用方离定义很远。
- **具名字段优于元组**：除单字段新类型外，元组结构体和 `.0`、`.1` 访问很快变得难懂。跨模块传递的元组（例如 `Vec<(i64, bool)>`）应考虑具名结构体。
- **实现标准 trait 而不是自定义方法**：功能与 `FromStr`、`Display`、`From`、`Default` 等相符时实现标准 trait。
- **借用优于深拷贝，慎用 `Rc`/`Arc`**：优先唯一所有权和借用；`clone()` 用于真正需要副本的地方。在架构层面，大量 `Arc<Mutex<_>>` 共享可变状态往往说明所有权和数据流没有设计清楚。异步服务中跨任务共享的连接池、配置等使用 `Arc` 是正常的。
- **灵活的引用参数**：接收 `&[T]`、`&str`、`&T`、`Option<&T>`，而不是 `&Vec<T>`、`&String`、`&Box<T>`、`&Option<T>`（clippy 的 `ptr_arg`、`borrowed_box` 会提示）。

## 错误处理（来自 Google 指南）

- 按 API 约定选择机制：
  - `Option`：简单、明显的失败，不需要更多信息。
  - `Result`：可恢复的失败，调用方需要区分原因。
  - `panic!`：程序缺陷和被违反的不变量，应通过修改代码避免。
- 不可避免的 `panic` 用 `expect("原因")` 而不是 `unwrap()`；用模式匹配代替「先检查再 unwrap」。
- 架构层面的检查：
  - 库或领域模块通常定义有含义的错误类型（例如用 `thiserror`），调用方可以按变体处理；应用的外层（入口、后台任务、命令行）用 `anyhow` 一类的工具附加上下文。领域模块全部返回 `anyhow::Error` 会让调用方无法区分错误原因，是否值得报告取决于调用方是否真的需要区分。
  - API 层把内部错误统一映射为对外错误格式，内部细节（SQL、堆栈、供应商原始报文）不应泄漏给使用者。
  - 关键路径上的 `let _ = ...`、`.ok()`、`.unwrap_or_default()` 可能吞掉错误，结合上下文判断。
  - 结果必须被使用的函数和类型考虑 `#[must_use]`；`Result` 本身已经是 `#[must_use]`。

## 其他结构规则（来自 Google 指南）

- **宏的使用顺序**：优先普通函数、类型、trait 和模块；其次 `macro_rules!`；再次其他代码生成；最后过程宏。宏让 IDE、代码搜索和大规模重构变难，并可能形成方言。应用内部自建大量宏属于过度设计信号。
- **不在 `main()` 之前运行代码**：不使用 `ctor` 一类的机制。启动逻辑在入口中显式编排。
- **`unsafe` 封装**：只在无法安全实现时使用；封装在与业务逻辑隔离的安全抽象中，每个 `unsafe` 块写 `SAFETY:` 注释说明为什么正确。
- **不使用 `catch_unwind` 作为控制流**。
- **不要过度依赖类型推断**：泛型返回的调用（`.into()`、`.parse()`、`collect()`）和复杂的迭代器结果标注类型；跨模块的公共函数签名本来就是显式的。
- **迭代器链要清晰**：长链、修改外部状态的链改用 `for` 循环；避免 `for_each`。
- **文档**：公共 API 写文档注释；可能 panic 的函数说明 panic 条件；`unsafe` 函数和 trait 说明不变量。模块顶部的 `//!` 说明模块职责，这是评审「模块职责是否清晰」的首要依据。

## 异步与并发

- 异步任务的生命周期和停止信号应当由入口集中管理（例如通过 `watch`、`CancellationToken`），不要在深层函数中随意 `tokio::spawn` 后丢弃句柄，否则任务失败和关闭顺序都不可控。
- 阻塞操作（重计算、同步 I/O）不应直接在异步执行器上运行，应放到阻塞线程池或专用执行器中。
- 不要尝试读取中毒的 mutex 内部数据。
- 跨模块共享的可变状态（`Arc<Mutex<_>>`、全局 `static`）是强耦合，记录谁拥有它、谁可以修改。

## 数据库访问

- SQL 是否集中在数据访问函数中，还是散落在 API 处理函数、业务计算和后台任务中。同一张表的写入逻辑分散在多个模块时，表的不变量就没有唯一的守护者。
- 动态拼接 SQL 是否有统一、可审计的约束（参数绑定、白名单）。
- 迁移文件是否是表结构的唯一来源。
