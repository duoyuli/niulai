# React 与 TypeScript 适配

本文说明通用原则在 React 单页应用和 TypeScript 中的落地方式。

## 组件的单位

- 前端的「组件」（架构意义上）对应 `src/` 下的顶层目录，例如 `pages/`、`components/`、`hooks/`、`lib/`、`api/`。`scripts/dep_graph.py --lang ts` 按顶层目录统计依赖。
- 常见的健康依赖方向：`pages` → `components`、`hooks` → `lib`、`api`。底层目录（`lib`、`components` 中的通用 UI）不应引用 `pages`；通用 UI 组件不应引用业务专用的 Hook 或接口客户端。

## 关注点分离

- **页面负责组合，组件负责展示，Hook 负责数据和状态，`lib` 负责纯逻辑**。这是 React 应用中最常见的分层，对应通用原则中的关注点分离和副作用隔离。
- 违反信号：
  - 页面组件里直接写 `fetch`、拼接 URL、解析后端原始字段。
  - 展示组件内部发起请求，导致无法在其他上下文复用或测试。
  - 业务计算（格式化之外的规则、公式、状态推导）写在 JSX 渲染函数中，而不是可单独测试的纯函数。
  - 同一套数据转换在多个页面中各写一遍。
- 不算违反：只用一次、几行的简单派生逻辑留在组件内更易读。

## 接口边界与单一事实来源

- 接口类型和客户端从后端的 OpenAPI 描述生成时，生成目录是前后端契约的唯一来源：不手改生成代码，不在别处重复定义同样的类型。
- 生成的类型应当在一个薄层（Hook 或 `lib` 中的适配函数）中被转换成页面需要的形状；如果每个页面都直接依赖接口原始字段，后端字段变化会波及所有页面。是否需要这层适配，取决于接口形状与页面需求的差距，差距很小时直接使用生成类型更简单。
- 后端已经定义的枚举、阈值和业务规则不要在前端硬编码第二份。确实需要在前端使用时，优先从接口返回或从生成的类型中获取。

## 状态管理

- 区分服务端状态（来自接口的数据，交给 TanStack Query 一类的工具缓存和失效）与客户端状态（界面交互状态，用组件状态或上下文）。把服务端数据复制到全局状态再手动同步，是单一事实来源的典型违反。
- 状态放在需要它的最低公共祖先，不要过早提升到全局上下文。一个巨大的全局上下文让所有消费者因为任意字段变化而重新渲染，也违反接口隔离。
- 能从其他状态推导出的值不要单独存储（推导状态）。

## SOLID 在前端

- **SRP**：一个组件同时负责取数、状态管理、复杂布局和业务规则时，拆分为容器（或 Hook）与展示组件。判断标准仍是变化原因，而不是行数。
- **OCP**：通过 `children`、渲染属性和组合扩展组件，而不是为每种新变化添加布尔 props。props 中出现大量互斥的布尔开关（`isCompact`、`isLarge`、`showX`、`hideY`）是信号，考虑用变体枚举或组合。
- **LSP**：封装原生元素的组件应当透传原生属性并保持原生行为（例如封装的按钮支持 `disabled`、`type`），否则使用者无法把它当作原生元素替换。
- **ISP**：props 只接收需要的字段，不传整个大对象。
- **DIP**：组件依赖 Hook 提供的数据和回调，而不是直接依赖具体的接口客户端；这让组件可以在测试中用不同数据渲染。不需要引入依赖注入框架。

## 组合优于继承

- 用组合和自定义 Hook 共享逻辑，不使用类组件继承；高阶组件层层包装通常可以改为 Hook。

## TypeScript 类型设计

- 用联合类型和可辨识联合表达状态（`{ status: 'loading' } | { status: 'error', error } | { status: 'ok', data }`），而不是多个可能矛盾的布尔字段。
- 避免 `any` 和不加验证的类型断言跨越模块边界；外部数据在进入系统的边界处校验或由生成的类型约束。
- 用 `switch` 加 `never` 检查做穷尽匹配，让新增变体时编译器指出遗漏，作用与 Rust 的穷尽 `match` 相同。

## 路由与页面组织

- 路由表应当集中定义；页面按用户任务组织时，页面目录结构与导航结构保持一致，便于定位。
- 页面间共享的逻辑放到 `hooks/` 或 `lib/`，页面之间不直接相互引用。
