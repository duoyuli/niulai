## 1. 组件边界与依赖方向

这一组决定系统能否随时间演进。组件（crate、顶层模块、前端的顶层目录）之间的依赖一旦混乱，后续的每次变更都要付出代价，而且很难在不停工的情况下修复。

### 1.1 关注点分离与分层

**含义**：把变化原因不同的关注点放在不同的位置。常见的划分是：接口适配（HTTP、CLI、页面）、应用编排（用例、流程）、领域规则（业务计算、不变量）、基础设施（数据库、外部 API、文件、时钟）。

**为什么重要**：不同关注点的变化频率和变化原因不同。混在一起时，改其中一个就会波及另一个，测试也必须带上所有关注点。

**违反信号**：

- HTTP 处理函数里直接写复杂的业务计算或长段 SQL。
- 领域计算函数直接读环境变量、发 HTTP 请求或访问数据库。
- 同一个函数同时负责解析输入、执行规则、写数据库和格式化输出。
- 前端页面组件里直接拼接 URL、解析后端原始字段、实现业务公式。

**检查方法**：挑最长、最常改的几个文件，按段落标注每段属于哪个关注点。如果一个文件里出现三种以上，并且它们之间没有通过清晰的函数边界分开，就是候选问题。

**不算违反**：简单的增删改查直接从处理函数访问数据库，没有业务规则，再加一层只是转发。分层的深度应当与业务规则的复杂度匹配。

### 1.2 依赖规则

**含义**：源代码依赖只能指向更稳定、更抽象、更接近业务核心的方向。业务规则不知道 Web 框架、数据库驱动和外部供应商的存在；外层（适配器、基础设施）依赖内层，而不是相反。这是 Clean Architecture、Hexagonal（端口与适配器）和 Onion Architecture 的共同核心。

**为什么重要**：业务规则是系统中最有价值、最应长期稳定的部分。它一旦依赖外部细节，就会因为外部细节的变化（换数据库、换供应商、换框架、升级 API）而被迫修改，也无法脱离外部环境单独测试。

**违反信号**：

- 领域模块引用 Web 框架类型（请求、响应、状态码）或 API 层的结构体。
- 业务模块直接依赖某个供应商客户端的具体类型和字段名。
- 底层基础模块引用高层业务模块（例如通用工具模块引用账户模块）。
- API 层的序列化结构体被当作领域模型在内部到处传递，导致改接口字段就要改业务代码。

**检查方法**：用依赖图找出每个模块所在的层，检查是否存在从内层指向外层的边。对每条可疑边打开引用位置，确认是真实的结构依赖还是只是共享一个基础类型。

**不算违反**：所有层都依赖语言标准库、基础类型（时间、错误、ID）和项目公共的基础模块。依赖一个稳定的基础库不违反依赖规则。务实的项目可以让领域代码直接使用数据库连接池，只要 SQL 和业务规则在函数边界上分得开；是否需要引入仓储抽象，看是否真有第二种实现或测试替身的需要。

### 1.3 无环依赖原则（ADP）

**含义**：组件之间的依赖图必须是有向无环图。

**为什么重要**：依赖环中的所有组件实际上变成了一个整体：不能单独理解、单独测试、单独修改，也无法确定构建和初始化顺序。环会随着时间吸入更多模块。

**违反信号**：`dep_graph.py` 报告的强连通分量（大小大于 1）；两个模块互相调用对方的函数；为了绕开环而把类型挪到一个「公共」模块，结果公共模块越来越大。

**检查方法**：运行 `scripts/dep_graph.py`，看「依赖环」部分。对每个环找出最弱的一条边（引用次数最少、最容易反转的那条），判断打破它的方法：依赖倒置（在被依赖方定义接口）、提取共同依赖的新模块、或者通过事件或回调反转调用方向。

**不算违反**：同一个组件内部的子模块互相引用通常可以接受，组件是一个整体发布和理解的单元。Rust crate 内的模块环不会导致编译失败，但顶层模块之间的环仍然值得报告，因为它反映了边界划分问题。

### 1.4 稳定依赖原则（SDP）

**含义**：依赖应当指向更稳定的方向。稳定度用不稳定度 I = Ce / (Ca + Ce) 衡量：Ce 是扇出（我依赖多少模块），Ca 是扇入（多少模块依赖我）。I 接近 0 表示稳定（很多模块依赖它、它依赖很少），接近 1 表示不稳定。依赖边应当从 I 大的模块指向 I 小的模块。

**为什么重要**：被大量依赖的模块改起来代价大，所以它会变得难以修改。如果一个稳定模块依赖了一个经常变化的模块，那个易变模块的每次变化都会传导到所有依赖稳定模块的地方。

**违反信号**：扇入很高的基础模块依赖一个业务细节模块；`dep_graph.py` 输出中某条边从低 I 指向高 I。

**检查方法**：读 `dep_graph.py` 的不稳定度表和「违反稳定依赖方向的边」列表，结合模块的实际变化频率（`git log --format= --name-only | sort | uniq -c`）判断。

**不算违反**：I 只是近似指标。一个扇入高但内容极其稳定的模块（例如时间工具）依赖另一个同样稳定的小模块，数值上可能显示为违反，实际无害。

### 1.5 稳定抽象原则（SAP）

**含义**：一个组件越稳定，就应当越抽象。稳定组件应当主要由接口、类型和契约组成，以便在不修改它的情况下扩展；不稳定组件可以是具体实现。

**为什么重要**：稳定且具体的组件处于「痛苦区」：大家都依赖它，但它全是具体逻辑，每次需求变化都必须修改它。不稳定且抽象的组件处于「无用区」：定义了抽象但没人使用。

**违反信号**：扇入很高的模块里包含大量具体的业务分支，并且这些分支经常因为新需求而修改。定义了 trait 或接口但只有一个实现、只有一个调用方。

**检查方法**：对扇入最高的几个模块，看它们暴露的是稳定的类型和函数签名，还是需要频繁修改的具体逻辑；结合 `git log` 的修改频率。

**不算违反**：应用代码中，稳定的公共模块常常是具体的工具函数（时间、格式化、错误）。它们稳定是因为逻辑本身不变，不需要抽象化。

### 1.6 共同闭包原则（CCP）、共同复用原则（CRP）与复用发布等价原则（REP）

**含义**：

- CCP：因为相同原因、在相同时间变化的东西放在一起；因为不同原因变化的东西分开。这是组件层面的单一职责原则。
- CRP：不会被一起使用的东西不要放在一起，避免使用者被迫依赖它不需要的部分。这是组件层面的接口隔离原则。
- REP：复用的粒度就是发布的粒度。对单个应用仓库影响较小，主要用于多 crate、多包的仓库。

**为什么重要**：一个需求变更如果需要同时修改多个组件，组件边界就划错了。CCP 倾向于把组件变大，CRP 倾向于把组件变小，需要按项目阶段取舍：早期更重视 CCP（便于开发），成熟后更重视 CRP（便于复用）。

**违反信号**：

- 新增一种业务对象（例如一种新的数据集或一种新的账户规则）需要在五个以上相距很远的目录各改一处，而且这些改动容易遗漏。
- `git log` 显示某几个分属不同模块的文件几乎总是一起修改。
- 一个模块的使用者只用到其中一小部分，却因为它的其他部分变化而被迫重新编译或修改。

**检查方法**：用「新增一个同类事物」做变更场景测试，数一下要改几处。用 `git log` 找经常同时修改的文件对（变更耦合）。

**不算违反**：某些横切的扩展点天然需要多处登记（例如新增一个 API 端点需要写路由、处理函数、文档注解、前端客户端）。只要登记点固定、有编译器或测试兜底、遗漏会立即报错，就不是严重问题。

## 2. 模块设计

### 2.1 信息隐藏

**含义**（David Parnas，1972）：模块划分的依据是「隐藏哪个可能变化的设计决策」，而不是「流程的哪一步」。每个模块把一个可能变化的决策（数据格式、算法、存储方式、外部协议）藏在稳定的接口后面。

**为什么重要**：被隐藏的决策可以单独修改，不影响使用者。泄漏出去的决策会被使用者依赖，之后再改就要改所有使用者。

**违反信号**：

- 模块的可见性过宽：内部辅助函数、内部结构体的字段被公开，并且确实被外部使用了。
- 使用者需要知道实现细节才能正确调用（例如必须先调用 A 再调用 B，否则数据不一致，而顺序没有被类型或接口强制）。
- 外部代码直接拼接本应由某模块负责的 SQL、键名、文件路径或协议字段。
- 供应商的原始字段名散落在多个模块中。

**检查方法**：对一个模块，列出外部实际使用的公开项。超出「完成这个模块的职责所需的最小接口」的部分都是候选泄漏。全局搜索某个格式细节（表名、字段名、键前缀），看它出现在几个模块里。

**不算违反**：为了测试而放宽到包内可见（例如 Rust 的 `pub(crate)`）。数据传输对象（DTO）本来就是公开字段。

### 2.2 深模块与浅模块

**含义**（John Ousterhout，《软件设计的哲学》）：好的模块是「深」的：接口简单，实现承担了大量复杂度。浅模块的接口和实现差不多复杂，只增加了一层间接，没有隐藏任何东西。

**为什么重要**：每个模块的接口都是使用者的认知负担。浅模块增加了负担却没有减少复杂度，大量浅模块让代码难以导航。

**违反信号**：

- 只做转发的函数或层：每个方法都只是把参数原样传给下一层。
- 一个功能被拆成很多几行的小文件，理解一个流程需要在十几个文件间跳转。
- 接口参数很多，调用方必须理解所有参数的组合才能用对。
- 「分类炎」：为了遵守单一职责，把一个内聚的概念拆成多个必须一起使用的类型。

**检查方法**：对一个模块，比较「使用者必须知道的东西」和「模块替使用者处理的东西」。前者接近后者时，模块是浅的。

**不算违反**：适配层（把外部接口转换为内部接口）天然较浅，它的价值在于隔离而不是隐藏复杂度。

### 2.3 高内聚、低耦合与耦合的强度

**含义**：模块内部的元素应当紧密相关（高内聚），模块之间的依赖应当尽量少且尽量弱（低耦合）。耦合有强弱之分，从弱到强大致是：依赖名字、依赖类型、依赖约定的含义（某个整数代表某种状态）、依赖位置或顺序（参数顺序、调用顺序）、依赖算法（双方必须用同一套计算）、依赖时序、依赖同一份可变状态。这套分级来自「共生性」（connascence）理论。

**为什么重要**：耦合越强、跨越的距离越远，修改时越容易遗漏。强耦合应当留在同一个模块内部；跨模块的耦合应当尽量弱化为名字和类型。

**违反信号**：

- 两个模块各自实现同一套计算规则，必须保持一致（算法耦合跨越模块）。
- 用魔法数字、字符串常量表示状态，并且在多个模块中各自比较。
- 跨模块共享可变全局状态。
- 隐式的调用顺序约定，跨越模块边界。
- 一个模块内部的函数彼此无关，只是因为「都是工具」被放在一起（低内聚）。

**检查方法**：对跨模块的依赖，判断它属于哪种强度。搜索重复出现的字面量和计算公式。看模块内的函数是否围绕同一组数据或同一个概念。

**不算违反**：同一个模块内部的强耦合是正常的，内聚本身就意味着内部元素紧密相关。

## 3. SOLID

SOLID 由 Robert C. Martin 整理，最初针对面向对象的类设计，同样适用于模块、函数和 trait 或接口。在没有继承的语言（Rust、偏函数式的 TypeScript）中，把「类」读作「模块、结构体及其方法、trait、React 组件」。

### 3.1 单一职责原则（SRP）

**含义**：一个模块应当只对一类使用者（一个「变化的原因」）负责。不是「只做一件事」，而是「只有一个变化的理由」。

**为什么重要**：服务不同使用者的代码放在一起时，为一类使用者做的修改可能意外破坏另一类使用者的功能，并且两类修改会在同一个文件中冲突。

**违反信号**：

- 一个文件在 `git log` 中被不同主题的提交频繁修改（例如既因为页面展示改，又因为数据同步改，又因为权限改）。
- 一个结构体或模块的方法可以明显分成几组，每组使用不同的字段子集。
- 文件长度远超项目中的同类文件，并且内容覆盖多个业务主题。
- 一个函数的名字需要用「和」才能描述清楚。

**检查方法**：问「谁会要求修改这个模块」。如果答案是两类以上不相关的角色或需求方向，就是候选问题。用 `git log --format=%s -- <file>` 看修改主题是否分散。

**不算违反**：文件长不等于职责多。一个围绕单一概念、内容很长的模块（例如一个复杂的计算引擎）符合 SRP。不要为了缩短文件而拆分内聚的逻辑。

### 3.2 开闭原则（OCP）

**含义**：对扩展开放，对修改封闭。增加新的同类行为时，应当通过添加新代码完成，而不是修改已有的、经过验证的代码。

**为什么重要**：修改已有代码有引入回归的风险，并且会影响所有使用者。

**违反信号**：

- 同一组 `match` 或 `if/else` 分支（按类型、种类、名称分派）在多个地方重复出现，每增加一种新类型就要找到并修改所有这些地方。
- 新增一种同类事物需要修改一个核心模块的内部逻辑。

**检查方法**：找到系统中「会增加新种类」的维度（新的数据源、新的规则、新的页面、新的因子），用变更场景测试：新增一种需要改哪些已有代码。

**不算违反**：只在一处出现的 `match` 分派是最简单、最清晰的写法；Rust 的穷尽匹配会在新增枚举变体时让编译器指出所有需要修改的地方，这本身就是一种可靠的扩展机制。只有在扩展维度已经被证明会频繁变化时，才值得引入 trait 或注册表。为想象中的扩展预留的抽象违反 YAGNI。

### 3.3 里氏替换原则（LSP）

**含义**：子类型（实现某个接口或 trait 的类型）必须能替换其父类型使用，而不破坏调用方的正确性。实现不能加强前置条件、削弱后置条件，或违反接口约定的不变量。

**为什么重要**：调用方按接口的约定编写代码。某个实现违反约定时，调用方必须知道具体类型才能正确使用，抽象就失去了意义。

**违反信号**：

- trait 或接口的某个实现对某些方法直接 `panic!`、`unimplemented!()` 或抛出「不支持」。
- 调用方需要先判断具体类型（类型检查、`downcast`、按名字分支）再决定怎么调用。
- 某个实现的语义与其他实现不一致（例如一个实现的 `save` 是幂等的，另一个不是），而接口没有说明。

**检查方法**：对每个有多个实现的 trait 或接口，比较各实现是否都完整、一致地满足接口文档描述的约定。

**不算违反**：接口文档明确声明某些行为是可选的，并提供了查询能力的方法。

### 3.4 接口隔离原则（ISP）

**含义**：使用者不应被迫依赖它不使用的方法。宁可要多个小而专注的接口，也不要一个大而全的接口。

**为什么重要**：大接口让使用者与无关的变化耦合，也让编写测试替身变得困难（必须实现一堆用不到的方法）。

**违反信号**：

- 一个 trait 或接口有很多方法，大多数实现者只真正实现其中几个，其余是空实现或默认实现。
- 函数参数要求一个巨大的上下文结构体（「什么都有的 `AppState`」），但函数只用到其中一两个字段，导致测试时必须构造整个上下文。
- 前端组件接收一个完整的大对象作为 props，但只读取其中两三个字段。

**检查方法**：对接口和公共参数类型，统计每个使用者实际使用的部分。

**不算违反**：框架要求的状态注入（例如 Web 框架的共享应用状态）在入口层是正常的；问题在于把它一路传到内部的业务函数。

### 3.5 依赖倒置原则（DIP）

**含义**：高层策略不应依赖低层细节，两者都应依赖抽象；抽象应由高层（使用者）定义，而不是由低层（实现者）定义。

**为什么重要**：DIP 是实现依赖规则（1.2）和打破依赖环（1.3）的主要手段。它让业务规则可以在不知道具体实现的情况下被编写和测试。

**违反信号**：

- 业务逻辑直接构造具体的基础设施对象（在函数内部创建 HTTP 客户端、数据库连接、读取全局配置）。
- 为了让底层模块通知高层模块，底层模块直接引用了高层模块的函数（应改为回调、事件或由高层定义的 trait）。
- 业务逻辑无法在没有真实数据库或网络的情况下测试，而它本身的规则并不复杂。

**检查方法**：在依赖图中找从低层指向高层的边；看核心业务函数的参数是接收依赖还是自己获取依赖。

**不算违反**：DIP 不要求所有依赖都抽象化。依赖稳定的具体类型（标准库、成熟的基础库、项目自己的稳定值类型）完全可以。把纯计算从 I/O 中分离出来（见 4.5），常常比引入 trait 更简单、更有效地达到同样的可测试性。

## 4. 通用设计准则

### 4.1 DRY：每条知识只有一处权威表达

**含义**（《程序员修炼之道》）：DRY 针对的是知识和意图的重复，不是文本的重复。一条业务规则、一个格式约定、一个常量，应当只有一个权威的表达位置。

**为什么重要**：同一条知识的多份副本总会在某次修改中不一致，产生难以察觉的 bug。

**违反信号**：同一个业务公式、校验规则、阈值、状态映射在多个模块中各自实现；前端和后端各自硬编码同一个枚举值列表而没有从同一个来源生成。

**检查方法**：搜索关键常量、阈值、字段名和公式片段的出现位置。

**不算违反**：两段代码看起来一样，但服务于不同的业务概念、将来会朝不同方向变化，这是巧合的重复，合并反而制造了错误的耦合。经验法则是「三次法则」：第三次出现时再抽象。

### 4.2 KISS 与 YAGNI

**含义**：KISS：用能解决问题的最简单方案。YAGNI：不要为当前不需要的功能编写代码或预留扩展点。

**为什么重要**：每一层抽象、每一个扩展点都有维护成本。为想象中的需求付出的成本通常收不回来，而且错误的预测会让真正的需求更难实现。

**违反信号**：见第 6 节「过度设计的信号」。

**检查方法**：对每个抽象（trait、接口、泛型参数、配置项、插件机制），问「现在有几个实现或几种取值」「去掉它代码会变得更难懂吗」。

**不算违反**：已经明确在路线图中、并且改动成本会随时间急剧上升的扩展点（例如数据库表结构中的预留字段、对外 API 的版本化）。

### 4.3 最少知识原则（迪米特法则）

**含义**：一个模块只与它的直接协作者交流，不穿透协作者去操作协作者的内部。典型的违反是长链式访问 `a.b().c().d()`。

**为什么重要**：穿透访问让调用方依赖了整条链上每个对象的结构，任何一环的结构变化都会传导过来。

**违反信号**：跨模块的长链式字段访问；调用方深入另一个模块的内部结构去修改数据；`api` 层直接操作某个领域对象的内部集合。

**检查方法**：看跨模块边界的访问是否经过对方提供的函数或方法。

**不算违反**：对纯数据结构（DTO、配置、值对象）的链式读取，以及流式 API（迭代器链、构建器）不违反迪米特法则。

### 4.4 组合优于继承

**含义**：通过组合小的、独立的部件构建行为，而不是通过继承层次共享实现。

**为什么重要**：继承层次让子类与父类的实现细节强耦合（脆弱基类问题），并且层次一旦建立很难调整。

**违反信号**：深的继承链；为了复用一个方法而继承一个大类；React 中通过高阶组件层层包装来共享逻辑，而自定义 Hook 更合适。

**不算违反**：Rust 没有实现继承，本条主要适用于 TypeScript 类和遗留的 React 类组件。Rust 中 trait 的默认方法和 supertrait 是接口组合，不是实现继承。

### 4.5 副作用隔离：函数式核心、命令式外壳与命令查询分离

**含义**：把纯计算（输入决定输出、无 I/O）集中在核心，把 I/O、时钟、随机数和可变状态推到外壳。命令查询分离（CQS）：一个函数要么返回数据（查询，无副作用），要么改变状态（命令），不要两者兼有。

**为什么重要**：纯函数可以用普通单元测试覆盖所有边界情况，不需要数据库或模拟对象；有副作用的部分变薄，集成测试只需覆盖接线。这是最廉价、最可靠的可测试性来源。

**违反信号**：

- 复杂的业务计算函数内部直接查询数据库、获取当前时间、读取配置。
- 计算逻辑只能通过集成测试验证。
- 名字像查询的函数（`get_*`、`load_*`）会写数据或触发同步。

**检查方法**：找到核心业务计算，看它是否能以「数据进、数据出」的形式调用；看测试是否主要是纯函数的单元测试。

**不算违反**：简单的读写流程本来就主要是 I/O，没有值得提取的纯逻辑。

### 4.6 单一事实来源

**含义**：每份数据、每个定义都有唯一的权威来源，其他地方从它派生（生成、查询、引用），而不是复制。

**为什么重要**：多个来源会漂移，最终出现「哪个是对的」的问题。

**违反信号**：表结构同时由迁移和代码中的手写定义描述；接口类型在前后端各写一份；同一个配置项在多个文件中有默认值；派生数据（缓存、预计算结果）没有可靠的失效或重建机制。

**检查方法**：对关键定义（表结构、API 类型、枚举、配置默认值），确认权威来源在哪里，其他副本是否由它生成。

**不算违反**：有明确失效策略和重建路径的缓存与物化结果。

### 4.7 显式优于隐式

**含义**：依赖、副作用、执行顺序和控制流应当在代码中可见。

**为什么重要**：隐式的机制（全局单例、启动时自动注册、魔法约定、隐藏的副作用）让阅读者无法从局部代码推断行为，修改时容易产生意外。

**违反信号**：全局可变单例；通过命名约定或反射自动发现组件；构造函数或 getter 中的隐藏 I/O；宏隐藏了重要的控制流。

**不算违反**：框架层面公认的约定（例如路由宏、派生宏）在团队内普遍理解时可以接受。

### 4.8 错误处理的边界与快速失败

**含义**：在错误发生的地方尽早发现（输入校验、不变量检查）；错误类型按层次转换，在边界处添加上下文；不要吞掉错误。区分可恢复错误（返回给调用方处理）和程序缺陷（应当立即暴露）。

**为什么重要**：被吞掉或过晚发现的错误会以错误数据、静默失败的形式出现在远离原因的地方，排查代价极高。

**违反信号**：忽略错误返回值；捕获所有错误后只记日志然后继续，导致后续处理基于不完整的数据；内部错误细节（SQL、堆栈）直接返回给 API 使用者；底层错误类型泄漏到很高的层次而没有上下文。

**检查方法**：搜索忽略错误的写法（例如 Rust 的 `let _ =`、`.ok()`、`unwrap_or_default()` 用在关键路径上；TypeScript 的空 `catch`）。看 API 层是否把错误统一映射为对外的错误格式。

**不算违反**：后台任务中有意的「记录后继续」，只要有重试或补偿机制、并且状态被持久化。

### 4.9 配置与代码分离

**含义**（The Twelve-Factor App）：随部署环境变化的值（地址、密钥、开关）放在环境中，不写在代码里；配置在启动时集中读取和校验，以类型化的对象传给使用者。

**为什么重要**：分散读取的配置难以发现、难以校验，也容易把密钥泄漏到代码和日志里。

**违反信号**：业务代码中到处读环境变量；密钥、主机名硬编码；配置缺失时直到深层调用才报错。

**不算违反**：真正的业务常量（例如交易规则中的固定比例）属于代码，不是配置。

## 5. 演进与治理

### 5.1 架构决策记录（ADR）

**含义**：重要的架构决策以简短文档记录背景、取舍和后果，被取代时保留并标记状态。

**检查要点**：代码的实际结构是否与当前有效的 ADR 一致；是否存在重大结构变化却没有对应的 ADR；是否有已经被代码违背、但仍标记为有效的 ADR。

### 5.2 架构适应度函数

**含义**（《演进式架构》）：把架构规则写成可以自动执行的检查（测试、lint、CI 脚本），例如「领域模块不得依赖 API 模块」「不得出现模块依赖环」「生成代码不得手改」。

**为什么重要**：只写在文档里的规则会在某次赶工中被打破，而且没人发现。自动检查把规则变成构建失败。

**检查要点**：项目中关键的架构规则有没有自动检查；评审中反复出现的同类违反是否可以固化为检查。建议时给出具体可行的形式（例如一个测试读取依赖图并断言无环，或一条 lint 配置）。

### 5.3 可测试性是架构信号

**含义**：难以测试的代码通常是结构有问题的代码。需要大量模拟对象、需要启动整个系统才能测试一个规则，说明依赖方向或副作用隔离有问题。

**检查要点**：核心业务规则是否有不依赖外部环境的单元测试；测试的准备代码是否远长于被测逻辑。

### 5.4 康威定律

**含义**：系统结构倾向于复制组织的沟通结构。对小团队或单人项目，模块边界应当服务于理解和修改的便利，不需要为并行开发而过度拆分。

**检查要点**：仅当模块边界明显与团队或使用者的划分冲突时提及。

## 6. 过度设计的信号

过度设计常常借原则之名出现，评审时要同样认真地识别。以下每条都应当用「去掉它代码会更难懂、更难改吗」来检验。

- **只有一个实现的抽象**：trait 或接口只有一个实现，也没有测试替身使用它。Google Rust 风格指南明确要求：只有在需要泛型约束、需要 `impl Trait` 或 `dyn Trait`、或定义扩展 trait 时才定义 trait，不要仅为了组织代码而使用 trait。
- **投机性的通用化**：为「将来可能」的需求增加的参数、配置项、泛型参数、插件机制，当前只有一种取值。
- **穿透层**：一层的方法只是原样调用下一层的同名方法。
- **过细的拆分**：一个内聚的流程被拆成大量几行的函数或文件，理解它需要频繁跳转。
- **框架化**：在应用内部自建通用框架（自定义 DSL、宏系统、依赖注入容器），而实际使用场景只有寥寥几处。
- **模式堆砌**：为了使用设计模式而使用设计模式（简单的条件分支被替换为策略模式加工厂加注册表）。

报告过度设计时，同样给出代价：多出来的间接层让哪些变更变得更慢、哪些阅读变得更难。
