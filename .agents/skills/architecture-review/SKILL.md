# 架构评审

用一套稳定的业界通用原则检查系统结构，尽早发现架构腐化：依赖方向反转、边界被绕过、模块职责膨胀、抽象泄漏、过度设计。产出是只读报告，不修改代码。

架构评审的价值在于回答「下一次变更会有多贵」。原则只是判断的工具，结论必须落到具体代码和具体的变更场景上。一条无法说清「将来改 X 时要连带改哪些地方、会出什么错」的发现，通常不值得报告。

## 资料

- [references/principles.md](references/principles.md)：原则目录。每条原则的含义、为什么重要、违反信号、检查方法和「不算违反」的情形。每次评审都要读。
- [references/rust.md](references/rust.md)：原则在 Rust 中的落地方式，融合了 Google Rust 风格指南中与结构相关的规则。评审范围包含 Rust 代码时读。
- [references/typescript_react.md](references/typescript_react.md)：原则在 React 和 TypeScript 前端中的落地方式。评审范围包含前端代码时读。
- [scripts/dep_graph.py](scripts/dep_graph.py)：统计顶层模块之间的依赖、扇入扇出、不稳定度和依赖环，支持 Rust crate 和 TypeScript `src/` 目录。用法见脚本的 `--help`。

## 工作流程

### 1. 确定范围和目标

先判断评审对象，范围决定了深度：

- **一次改动**（diff、分支、PR）：重点是这次改动是否引入新的违反或让已有问题变得更糟。已有的旧问题只在被这次改动触及时提及。
- **一个模块或子系统**：检查它的对外接口、内部职责划分、与其他模块的依赖。
- **整个仓库**：先看宏观结构（模块依赖图、分层、边界），再抽查最大、改动最频繁或扇入最高的模块。不要试图逐文件审查。

如果用户的描述无法判断范围，按最合理的理解执行，并在报告的「范围与依据」中写明。

### 2. 读项目已声明的架构

通用原则之上，项目自己的决策优先。先读项目指令（`AGENTS.md`、`CLAUDE.md`）、架构文档和 ADR（架构决策记录）。仓库使用 project-doc 时，按文档索引的路由进入「架构」和「决策」分类。

项目做出的有意取舍不算违反。例如 ADR 决定「单进程服务」，就不要以「应拆分服务」为由报告问题。如果你认为某个决策本身已经不再合理，在报告的「对现有决策的意见」中单独说明理由，不要混入违反清单。

同时记下项目已经明确的架构规则（例如「动态 SQL 必须用某种包装」「某目录为生成代码」），评审时把它们当作和通用原则同等的检查项。

### 3. 建立结构视图

在判断之前先看清结构：

1. 列出顶层模块及其职责（模块文档注释、目录名、文档）。
2. 运行 `scripts/dep_graph.py` 得到模块依赖矩阵、扇入扇出、不稳定度和依赖环。脚本只统计静态引用，是线索，不是结论；对可疑的依赖边打开代码确认。
3. 找出 I/O 边界：数据库、外部 API、文件、网络、时钟、环境变量分别在哪些模块被直接访问。
4. 找出系统入口：进程启动、HTTP 路由、定时任务、事件消费者，以及它们如何组装依赖。
5. 评审一次改动时，用 `git diff` 确认改动涉及哪些模块和哪些依赖边是新增的。

### 4. 按原则逐层检查

从宏观到微观，按 `references/principles.md` 的顺序检查：组件边界与依赖方向，模块设计，SOLID，通用设计准则，演进与治理。再按语言参考文件检查语言特有的结构问题。

不需要为每条原则都给出结论。只报告有证据的发现。没有发现的原则不必逐条写「符合」。

检查时始终同时提防两类问题：

- **结构不足**：职责混杂、依赖混乱、边界被绕过、重复的业务规则。
- **过度设计**：只有一个实现的 trait 或接口、为不存在的需求预留的扩展点、只做转发的中间层、把简单逻辑拆成大量浅模块。过度设计同样是架构腐化，而且更容易被「原则」合理化。

### 5. 用证据和变更场景论证每条发现

每条发现都要包含：

- **位置**：`文件:行号`，或依赖边（`模块 A → 模块 B`，附代表性引用位置）。
- **现象**：代码实际是怎样的，用事实描述。
- **违反的原则**：一到两条，不要堆砌。
- **代价**：一个具体、可信的变更场景。例如「要增加第二个数据源时，需要同时修改 `a.rs`、`b.rs` 和 `c.rs` 中的三处硬编码分支」。能指出已经发生过的问题（相关 bug、频繁的连带修改、`git log` 显示的同改文件）更有说服力。
- **建议**：最小可行的改进方向和大致成本。说明什么情况下可以暂时不改。

### 6. 定级

| 级别 | 判断标准 |
| --- | --- |
| 高 | 已经造成或很快会造成错误、依赖环、边界被绕过，并且会随新代码扩散；或者阻碍近期明确要做的变更 |
| 中 | 让常见变更明显变贵（需要连带修改多处、难以测试），但影响局限在一个子系统内 |
| 低 | 局部的可改进点，或只在特定变更下才有代价 |
| 观察 | 证据不足、需要更多上下文或需要团队决策的疑点 |

宁可少报，也不要用低价值发现淹没高价值发现。整个仓库的评审，高和中级别的发现通常不应超过十条左右；如果更多，合并同类项，按根因归组。

### 7. 输出报告

用中文输出，按下面的模板组织。报告直接在对话中给出；用户要求保存文件时再写入文件。

```markdown
# 架构评审：<范围>

## 结论

两到四句话：整体健康度，最需要处理的一到三个问题，以及最值得保持的结构优点。

## 范围与依据

- 评审对象：<diff / 模块 / 仓库>，<涉及的目录>
- 参考的项目决策：<读过的 ADR 和架构文档>
- 使用的工具：<dep_graph.py 等的关键输出>

## 结构概览

模块分层或依赖关系的简要描述，必要时附依赖矩阵或依赖环。只保留和发现相关的部分。

## 发现

### [高] <一句话标题>

- 原则：<原则名>
- 位置：`path/to/file.rs:123`
- 现象：……
- 代价：……（变更场景）
- 建议：……（成本，何时可以暂缓）

（按严重程度排序，同级按影响面排序）

## 值得保持的结构

列出两到五个做得好的设计，说明它保护了什么。这部分告诉后续开发者哪些边界不要破坏。

## 对现有决策的意见

（可选）认为某个 ADR 或既定约定需要重新评估时写在这里。

## 未覆盖与待确认

没有检查到的部分、证据不足的疑点、需要用户或团队确认的问题。
```

## 原则

- **只读**：不修改代码和文档。用户在看过报告后要求修复时，再按正常的修改流程处理。
- **事实优先**：每个判断都能回到具体代码。读不到的代码不要推测；需要推测时明确标注。
- **尊重上下文**：小型应用不需要大型框架的抽象层次。Google Rust 风格指南区分「库代码」和「应用代码」：应用代码优先简单直接，避免过早泛化。评审应用代码时采用同样的尺度。
- **原则之间会冲突**：例如 DRY 与低耦合、OCP 与 YAGNI、CCP 与 CRP。遇到冲突时说明取舍，按项目当前阶段和已知的变更方向选择，不要机械地选一边。
- **增量视角**：评审改动时，关注它让结构变好还是变坏。不要求一次改动修复所有历史问题，但新代码不应让已有问题扩散。
- **可自动化的规则建议固化**：如果某类违反反复出现且可以机器检查（依赖方向、禁止的导入、文件大小），在建议中提出把它写成架构适应度函数（测试、lint 或 CI 检查）。
