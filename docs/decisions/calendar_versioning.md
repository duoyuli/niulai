# ADR：版本号按发布日期定

- 状态：已采纳（accepted），2026-10-17。部分取代 [ADR：只在发布版本标签时构建镜像](image_on_tag.md) 的决策第 2、3 条（镜像标签和预发布），以及 [ADR：Docker 部署的一键升级](one_click_upgrade.md) 中「upgrader 只接受 `X.Y.Z`」。
- 相关文档：[CI：构建镜像](../operations/runbook.md#release_image)、[一键升级](../operations/runbook.md#one_click_upgrade)。

## 背景

以前用语义化版本 `X.Y.Z`（1.0.0 到 1.5.0），每次发布都要判断改动算大版本、小版本还是补丁，而这个项目只有一个使用者，发布节奏是「改好一批就发」，一天可能发几次。用户要求版本号直接按年月日定，同一天发多次时后面加一个小补丁号。

## 决策

1. 版本号是发布当天的上海日期 `YYYY.MM.DD`，月和日补零，例如 `2026.10.18`；同一天再发布时加补丁号：`2026.10.18.1`、`2026.10.18.2`……git 标签前面带 `v`。
2. 发布时在已经推送、CI 通过的 `main` 上，按今天的上海日期和已有标签定版本号，打带说明的标签并推送，步骤见 [CI：构建镜像](../operations/runbook.md#release_image)。（曾经用脚本 `deploy/release.sh` 自动算版本号，2026-10-17 删掉：它是开发用的工具，不该放在要拷到服务器上的 `deploy/` 里，规则也简单到不需要脚本。）
3. 比较大小按数字逐段比较，没有补丁号的算 0（`backend/src/version.rs`）。以前的 `X.Y.Z` 按同样规则解析，都小于日期版本，所以从 1.5.0 能直接升级到日期版本。
4. 镜像标签是去掉 `v` 的版本号，加上 `latest` 和 `sha-<提交>`。不再有 `X.Y` 这样的标签，也不再有预发布标签；CI 遇到格式不对的 `v*` 标签直接失败，不构建镜像。

## 后果

- 1.5.0 及更早的程序只认三段数字的版本号。每天第一个版本没有补丁号，老版本能检测到并一键升级；同一天的补丁版本（四段）要等升级到日期版本之后才能识别。
- 版本号本身说明了发布时间，看不出改动大小；改动内容看页面上「新版本」链接到的两个标签的对比页面，或标签的说明。
- 想在发布前试用，仍是本机构建镜像或源码部署，不能发预发布标签。

## 考虑过的方案

- **继续用语义化版本：** 不采用。项目没有对外的接口兼容承诺，区分大小版本没有意义，反而每次发布都要判断。
- **`YYYY.M.D`（不补零）或 `YY.MM.DD`：** 不采用。补零后标签按字符串排序也是发布顺序，四位年份不会和以前的 `1.x` 混淆。
- **同一天的补丁用 `-1`：** 不采用。带 `-` 在语义化版本里是预发布，会排在当天正式版本之前，老版本程序也会把它当成预发布忽略。
