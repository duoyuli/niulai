# ADR：通用记录库加类型化投影

- 状态：已采纳（accepted），2026-10-15。
- 相关文档：[数据库分层](../architecture/data_model.md)、[同步流水线](../architecture/sync_pipeline.md)、[数据集注册表格式](../interfaces/dataset_registry.md)。

## 背景

供应商有 95 个公开接口，纳入同步的有 86 个数据集，当前功能只用到其中十几个。用户要求「暂时可以先不用，但是将整个同步机制一次做好」。其中估值、指数成分、异动原因等接口只返回当前值，错过的日子以后无法补回。

## 决策

1. 同步机制用一个通用执行器加一份声明式配置（`backend/config/datasets.yaml`），新增数据集只改配置。
2. 所有数据集默认写入通用记录库 `raw.record`：每个数据集的每个主键一行，字段保持供应商原样（JSONB），另外提取业务日期和证券代码两列；值变化时旧值写入 `raw.record_version`。
3. 需要类型和索引的数据（日线、公司行动、证券、指数、估值）再通过 sink 投影到 `ref`、`mkt`、`fin` 下的类型化表。
4. 日线这类大数据集（全量原始 JSON 超过 1 GB）不写 `raw.record`、不存原始响应，只写类型化表。

## 取舍

- **通用记录库与每个接口一张表**：每个接口建专表要写 86 套建表和写入代码，大部分暂时用不上。通用记录库让所有数据从第一天起都能积累；以后需要时，直接在 `raw.record` 上建视图或物化，不需要重新拉取。代价是 JSONB 的存储和查询效率不如专表，所以常用数据仍然投影到类型化表。
- **修订历史**：保存旧值会增加存储，但能发现供应商事后修改的财报、行情和名称。
- **一份配置描述全部数据集**：配置的表达能力有限，组合分区（`cross`）目前还不支持，涉及的 2 个期货数据集暂时无法规划。

## 后果

- 新增数据集的标准流程见 [新增数据集](../interfaces/dataset_registry.md#adding_dataset)。
- `raw.record` 会随时间增大。目前只有一个默认分区，数据量大的数据集以后可以单独建分区。
- 判断数据是否变化依赖 `payload` 的 md5；供应商字段顺序变化不影响结果，因为 JSONB 的文本形式是规范化的。
