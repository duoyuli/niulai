# ADR：部署迁移与升级进度

- 状态：已采纳（accepted），2026-10-17。部分取代 [ADR：Docker 部署的一键升级](one_click_upgrade.md) 中「先升级 niulai、最后换掉 upgrader」的顺序，以及「一键升级只更换镜像」。
- 相关文档：[一键升级](../operations/runbook.md#one_click_upgrade)、[部署迁移](../operations/runbook.md#deploy_migrations)、[数据目录](../operations/runbook.md#data_dir)。

## 背景

内置数据库的数据原来放在 Docker 卷 `pgdata` 中，不在部署目录下：`docker compose down -v`、`docker volume prune` 这类常见的清理命令会把它删掉，备份和搬迁时也看不到。用户要求数据默认放在当前磁盘的部署目录里。

但已经部署的系统靠一键升级更新，升级只换 niulai 的镜像，服务器上的 `compose.yml` 和 `.env` 不会跟着仓库变；只改仓库里的 `compose.yml`，已有部署永远用不上，手动换上新文件又会让数据库从空的开始。用户要求：遇到这类不兼容的改动，先写好迁移，迁移完再升级过去。用户还反映，升级时页面只显示一句话，不知道进行到哪一步，要等多久。

## 决策

1. **部署迁移由新版本的 upgrader 做。** 新版本需要的迁移只有新版本的代码知道，所以升级顺序改为：下载新版本 → 把 upgrader 换成新版本（进度写在 `handoff` 文件里交接）→ 备份数据库 → 部署迁移 → 启动新版本的 niulai。迁移在新版本的 niulai 启动之前做完。upgrader 启动时也检查一遍还没做过的迁移，覆盖从旧版本升级上来（旧 upgrader 还按原来的顺序做）的情况。
2. **迁移只做一次，前提不满足就跳过。** 结果记在部署目录的 `.niulai-migrations`。每个迁移先检查前提（例如 `compose.yml` 那一行没被手改过、目标目录是空的），不满足就跳过并写明原因；做到一半失败时恢复原样。改 `compose.yml` 只替换认得的那一行，不整个覆盖，保留用户的其他改动。
3. **数据目录默认在部署目录。** `compose.yml` 中数据库挂载 `${POSTGRES_DATA:-./data/postgres}`；第一个部署迁移把已有部署的数据从卷复制过去（用数据库镜像起临时容器，`cp -a` 保留属主和权限，核对文件数和总大小），原来的卷保留不删。
4. **升级的每一步写进状态文件。** `status` 中加 `steps`：每一步的名称、状态和说明（下载的百分比和 MB、等新版本启动已等了多久）。页面顶部和版本号的弹窗显示进度条和步骤列表；服务重启期间请求失败也继续轮询，所有步骤结束后才刷新页面。

## 后果

- 从 2026-10-17 之前的版本升级时，旧 upgrader 不知道新顺序：它先升级 niulai、再换掉自己，新的 upgrader 启动后补做数据目录迁移，期间 niulai 再停一次（复制几 GB 数据要一两分钟）。旧 upgrader 也不写步骤，这一次页面只显示一句话。
- upgrader 换成新版本失败时（例如新镜像起不来），由当前的 upgrader 继续，但它不知道新版本的迁移；页面上「更新升级助手」显示为跳过和原因。
- 数据目录迁移用真实的 Docker 测过（`cargo test --lib -- --ignored real_docker_data_dir_migration`）：按改动前的写法起项目、写数据、迁移、再 `docker compose up -d`，数据都在。2026-10-17 还用本机构建的镜像完整走过两次一键升级：从已发布的 v2026.10.17（旧顺序）升级，新的 upgrader 启动后补做迁移；两个版本都是新代码时，按新顺序交接、迁移、启动，页面上的五步都有进度。之后 `docker compose down -v` 删掉全部容器和卷，重新启动，数据仍在。
- 复制之前检查部署目录所在的磁盘：要放下一整份数据再留 1 GB，不够时什么都不改，页面显示需要多少、还剩多少。复制期间原来的卷还在，所以同一块磁盘上要有两份数据的空间。
- 原来的卷要用户确认后手动删除，多占一份磁盘空间。

## 考虑过的方案

- **只改仓库里的 `compose.yml`，在发布说明中让用户手动迁移：** 不采用。一键升级就是为了不让用户手动改服务器上的文件；手动换文件时漏了迁移，数据库会从空的开始。
- **由旧版本的 upgrader 在升级前做迁移：** 做不到。旧版本不知道新版本需要什么迁移。
- **整个替换服务器上的 `compose.yml`：** 不采用。会覆盖用户改过的端口、资源限制等。
- **迁移时直接删掉原来的卷：** 不采用。复制出问题时就没有退路，留着让用户确认后再删。
