# ADR：单进程服务

- 状态：已采纳（accepted），2026-10-15。取代 [ADR：技术栈](technology_stack.md) §4 中「API 与 Worker 使用独立启动入口、独立进程」的部分。「扩容」一条已被 [ADR：限速在进程内](in_process_rate_limit.md) 取代：同一时刻只有一个进程执行同步任务。
- 相关文档：[项目概览](../project_overview.md#processes)、[同步流水线](../architecture/sync_pipeline.md)、[运维手册](../operations/runbook.md)。

## 背景

后端首版有三个程序：`niulai-api`（REST API）、`niulai-worker`（执行同步任务和定时调度）、`niulai`（运维命令行）。拆分的理由是让长时间的采集任务不和查询请求争用资源，并且可以只扩容 worker。用户认为三个程序没有必要，要求合并为一个。

## 决策

1. 只保留一个程序 `niulai`。
2. 常驻服务是 `niulai serve`：一个进程同时运行 REST API、同步任务执行循环和定时调度，三者共用同一个同步引擎和数据库连接池。`--no-api`、`--no-worker`、`--no-scheduler` 可以关闭其中一部分。
3. 运维操作（迁移、规划、前台执行、查看状态、重算复权、导出 OpenAPI）是 `niulai` 的其他子命令，执行完就退出。
4. 部署时只有一个容器，运行 `niulai serve`。
5. **允许另外启动只提供 API 或计算的进程（`--no-worker`、`--no-api`），因此进程内状态只能是可丢弃的缓存**（2026-10-23 架构评审后补充）。具体约束：
   - 进程内缓存（市场概况、账户的因子排名）的键里带 `ops.derived_version` 的版本，数据变了自然不再命中，不依赖某个进程收到事件后去清空；
   - 去重和独占（执行同步任务、数据核检）用 PostgreSQL 咨询锁，不用进程内的标志；
   - 待办（同步完成事件、改了账户之后的建议重算）写在数据库里，由受监督的组件消费、成功后确认，进程退出不丢；
   - 仍在进程内、但丢了无害的：供应商最新交易日的 10 分钟缓存（`calendar`）、登录失败计数、版本查询结果。
   架构适应度测试（`backend/src/lib.rs` 的 `architecture`）检查模块的依赖方向，新增进程内状态时按上面的规则评审。

## 取舍

- **资源争用**：同步任务主要是等待供应商响应的网络 I/O，吞吐受供应商限速（每秒 2 次）约束，与 API 查询争用的资源很少。CPU 较重的是运行结束后的复权重算（本机全市场约 2 秒），它在数据库中执行，不占用 API 的处理线程。
- **扩容**：任务队列在 PostgreSQL 中，用 `FOR UPDATE SKIP LOCKED` 认领；执行独占权由 PostgreSQL 咨询锁保证，同一时刻只有一个进程向供应商发请求，限速保留在该进程内。需要隔离 API 或计算任务时，再启动 `--no-api` 实例，但不把它们当作并行供应商执行器。
- **故障隔离**：API 和执行循环在同一个进程中，进程崩溃会同时影响两者。执行中的任务会在 10 分钟后被回收重试，API 由容器的 `restart: unless-stopped` 重启。目前接受这个风险。

## 后果

- 部署和运维只需要管理一个进程和一个镜像。
- 停机时，API 停止接受新请求，执行循环等正在执行的任务结束后退出；最多等 100 秒（在 Docker 的 2 分钟之前），超过的组件直接取消，未完成的任务租约过期后由下一个进程回收。
- 以后如果出现需要隔离的重计算（例如回测），再评估是否在 `serve` 之外单独运行，或用 `--no-api` 的独立实例承担；按第 5 条，这样的实例不会读到别的进程留下的过期结果。
- 停机时，API 处理函数启动的后台任务（后台规划、数据核检）和常驻组件一起在同一个期限内收尾。
