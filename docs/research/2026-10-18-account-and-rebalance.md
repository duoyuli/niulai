# 账户持仓与调仓建议

> 调研笔记，不属于 Project Doc 文档库。2026-10-18 写，供拍板后实现。

## 一、目标

在现有的策略巡检和回测基础上，增加两个功能：

1. **账户持仓录入**：用户创建多个账户，录入每个账户的可用资金和持仓（哪些股票、各多少股、成本价）。
2. **调仓建议生成**：选一个账户和一组策略，系统根据账户实况和策略巡检结果，给出「卖什么、买什么、留什么」的操作建议。

不对接券商、不自动下单。建议只读，生成后不可修改，可回看历史。

## 二、核心概念

| 概念 | 含义 |
| --- | --- |
| 账户（account） | 一个真实或模拟的证券账户。有名字、可用资金和一组持仓。同一个用户可以有多个账户，例如「主力账户」「小仓试验」「妈妈的账户」 |
| 持仓（position） | 账户中持有的一只股票：代码、股数、成本价（可选） |
| 调仓建议（rebalance） | 系统根据账户实况 + 用户选定的策略巡检结果，生成的一份操作计划 |

与现有概念的关系：

- 账户不影响策略、巡检、回测。它是一个「叠加层」——有了巡检结果之后，账户把它们「落地」到用户的真实仓位上。
- 调仓建议直接读巡检结果（`app.screen_run` / `app.screen_hit`），不重新发明选股逻辑。

## 三、多账户设计

### 为什么要多账户

一个人可能有多个券商账户，或者帮家人打理、或者想把实盘和模拟分开。每个账户的资金、持仓、风格完全独立。

### 账户之间的隔离

- 每个账户有自己的持仓表和调仓建议历史。
- 删除账户时级联清理持仓和所有历史建议。
- 账户之间没有任何关联。
- 账户数量上限 20 个，足够日常使用，防止失控。

## 四、数据模型

在 `app` schema 下新增 3 张表。

### app.account

```sql
CREATE TABLE app.account (
  account_id   BIGSERIAL PRIMARY KEY,
  name         TEXT NOT NULL,                    -- 账户名，1–30 字
  cash         NUMERIC(18,2) NOT NULL DEFAULT 0, -- 可用资金（元）
  note         TEXT NOT NULL DEFAULT '',          -- 备注
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### app.account_position

```sql
CREATE TABLE app.account_position (
  account_id   BIGINT NOT NULL REFERENCES app.account (account_id) ON DELETE CASCADE,
  thscode      TEXT NOT NULL,                    -- 证券代码
  shares       INTEGER NOT NULL CHECK (shares > 0 AND shares % 100 = 0), -- 持仓股数，100 的整数倍
  cost_price   NUMERIC(18,4),                    -- 持仓成本价（未复权），可选
  PRIMARY KEY (account_id, thscode)
);
```

设计要点：

- `shares` 必须是 100 的整数倍（A 股一手 100 股）。
- `cost_price` 可选：有些用户不关心成本，只关心「我有什么、该怎么调」。录入了的，前端自动算浮盈。
- 没有单独存最新价和市值——每次查询时用 `mkt.stock_bar_1d` 的最新收盘价算。
- 录入时校验 `thscode` 在 `ref.security` 中存在。

### app.rebalance

```sql
CREATE TABLE app.rebalance (
  rebalance_id BIGSERIAL PRIMARY KEY,
  account_id   BIGINT NOT NULL REFERENCES app.account (account_id) ON DELETE CASCADE,
  strategy_ids BIGINT[] NOT NULL,                -- 依据的策略
  trade_date   DATE NOT NULL,                    -- 生成建议时用的交易日
  params       JSONB NOT NULL,                   -- 生成时的参数快照
  result       JSONB NOT NULL,                   -- 建议结果（只读快照）
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX rebalance_account_idx ON app.rebalance (account_id, created_at DESC);
```

设计要点：

- `params` 是参数快照，例如 `{"max_positions": 5}`。
- `result` 是完整的建议结果（见下文结构），一旦生成就不可修改。用户可以回看历史建议，事后验证准确度。
- 策略被删除后，`strategy_ids` 中的编号仍然保留，只是无法再查到策略名——历史记录不因策略删除而丢失。

## 五、调仓建议的生成逻辑

### 输入

- 账户的 `cash` 和 `positions[]`
- `strategy_ids[]`（用户选的策略，至少一个）
- `max_positions`（目标最大持仓只数，默认 5，范围 1–20）
- `trade_date`（默认最新交易日）

### 步骤

**步骤 1：收集巡检结果**

对每个策略，读取 `trade_date` 那天的巡检结果（`app.screen_run` + `app.screen_hit`）。如果策略在那天没有巡检结果，返回 400 并说明哪个策略缺结果。

从巡检结果中取三类数据：

- `buy` 列表：当天满足买入条件的股票（已排序）
- `sell` 列表：当天触发卖出信号的股票（带原因）
- `holding` 列表：仍处于「持有中」的股票

**步骤 2：分类当前持仓**

用账户实际持仓与巡检结果比对，把每只持仓股分为三类：

| 分类 | 条件 | 含义 |
| --- | --- | --- |
| 建议卖出 | 至少一个策略的 `sell` 列表包含它 | 策略认为应该离场 |
| 建议持有 | 至少一个策略的 `holding` 列表包含它，且没有策略要卖 | 策略认为可以继续持有 |
| 无策略覆盖 | 不在任何选定策略的 `buy` / `sell` / `holding` 中 | 策略对它没有判断 |

**矛盾处理：** 如果一个策略说卖、另一个策略说持有，按**卖出优先**处理。原因中列出是哪个策略发出的卖出信号。这是保守原则。

「无策略覆盖」的股票单独列出，不建议卖出也不建议持有——交给用户自行判断。

**步骤 3：生成买入建议**

1. 从各策略的买入列表中合并，去掉已持有的股票（不重复买入）。
2. 估算可用资金：现有 `cash` + 卖出建议释放的资金（按最新收盘价 × 股数）。
3. 计算空余仓位：`max_positions` − 持有的只数（含「建议持有」和「无策略覆盖」）− 建议卖出的不算。
4. 空余仓位 > 0 且资金足够时，按策略排序依次分配：每只投入「可用资金 ÷ 空余仓位数」，按 100 股取整。不够一手的跳过，在结果中标注「资金不足」。

**步骤 4：汇总**

输出 `sell[]`、`hold[]`、`buy[]` 和 `summary`，写入 `app.rebalance.result`。

### 不做的事

- 不考虑手续费和印花税——只是估算，实际成交价和费用由券商决定。
- 不考虑涨跌停和一字板——建议是方向性的，用户自己判断能不能成交。
- 不模拟 T+1——建议是「看完之后明天该做什么」，不是实时交易指令。
- 不保存建议后自动更新持仓——用户执行完操作后自己回来改持仓。

## 六、REST API

### 账户

| 方法与路径 | 说明 | 主要参数 |
| --- | --- | --- |
| `POST /accounts` | 新建账户 | 请求体 `{name, cash, note?}` |
| `GET /accounts` | 全部账户列表，含持仓只数和总市值 | — |
| `GET /accounts/{id}` | 账户详情：持仓列表（附最新价、市值、浮盈） | — |
| `PUT /accounts/{id}` | 修改账户名、资金、备注 | 请求体 `{name, cash, note?}` |
| `DELETE /accounts/{id}` | 删除账户（级联删持仓和历史建议），返回 204 | — |

### 持仓

| 方法与路径 | 说明 | 主要参数 |
| --- | --- | --- |
| `PUT /accounts/{id}/positions` | 整体更新持仓 | 请求体 `{positions: [{thscode, shares, cost_price?}]}` |

为什么用整体更新（PUT）而不是逐只增删：

- 用户的心智模型是「打开券商 App，把现在的持仓抄进来」。整体更新最贴合这个操作——填一份持仓表，提交，完事。
- 前端发送时只需要把当前表格的内容全部带上，没变的原样带回。逐只增删在持仓变化频繁时反而更累。
- 清空持仓：发送 `{"positions": []}`。

校验规则：

- `thscode` 必须在 `ref.security` 中存在，不存在的返回 400 并列出哪些不存在。
- `shares` 必须是正整数且是 100 的整数倍。
- 同一个 `thscode` 不能重复出现。
- 一个账户最多 50 只持仓。

### 调仓建议

| 方法与路径 | 说明 | 主要参数 |
| --- | --- | --- |
| `POST /accounts/{id}/rebalance` | 生成调仓建议 | 请求体 `{strategy_ids, max_positions?}` |
| `GET /accounts/{id}/rebalances` | 历史调仓建议列表 | `limit` 默认 20，最大 100 |
| `GET /accounts/{id}/rebalances/{rid}` | 一条建议的详情 | — |

生成调仓建议的校验：

- `strategy_ids` 不为空，每个都必须存在。
- 每个策略在 `trade_date` 当天必须有巡检结果。没有时返回 400，说明「策略 XXX 在 YYYY-MM-DD 没有巡检结果，请先在策略页开启巡检或手动执行巡检」。
- `max_positions` 范围 1–20，默认 5。

### 错误码

| HTTP 状态 | 场景 |
| --- | --- |
| 400 | 参数不合法：名称为空、资金为负、股数不是 100 的整数倍、持仓的证券不存在、策略没有巡检结果 |
| 404 | 账户或调仓建议不存在 |
| 409 | 账户数量已达上限（20 个） |

## 八、降低学习成本的设计

1. **与现有概念零冲突。** 账户不影响策略、巡检、回测的使用方式。不用这个功能，系统完全照旧。
2. **最少输入。** 新建账户只需填名字和可用资金。持仓之后再录也行。成本价可选。
3. **复用已有组件。** 搜索股票复用 `SecuritySearch`，策略选择就是策略列表，建议中的原因就是巡检的白话说明。用户不需要学新概念。
4. **建议直觉可读。** 结果分三个颜色区——红色卖、绿色买、灰色留。每条带白话原因，和策略巡检页看到的一模一样。
5. **价格自动更新。** 持仓录入的是股数，市值和浮盈用最新收盘价自动算。用户不需要手动更新价格。
6. **整体更新持仓。** 不需要记住加了什么、删了什么。直接把当前持仓表填好提交。
7. **建议不可修改。** 生成后就是快照，不会因为后续数据变化而变。可以回看历史建议。

## 九、边界情况

| 情况 | 处理 |
| --- | --- |
| 持仓的股票不在本地数据库 | 录入时校验 `ref.security` 存在，不存在返回 400 并列出哪些不存在 |
| 持仓的股票已退市 | 允许录入（用户可能确实还持有），但标注「已退市」，调仓建议中归入「无策略覆盖」 |
| 选定策略在当天没有巡检结果 | 返回 400，说明哪个策略缺结果，提示用户先巡检 |
| 可用资金不够买一手 | 建议中标注「资金不足，建议关注但暂无法买入」 |
| 多个策略对同一只股票给出矛盾建议 | 卖出优先；原因中说明是哪个策略的判断 |
| 账户数量已达 20 个上限 | 新建时返回 409，提示「账户数量已达上限，请删除不需要的账户」 |
| 持仓超过 50 只 | 录入时返回 400，提示「单个账户最多 50 只持仓」 |
| 策略被删除后查看历史建议 | `result` 里保存了策略名的快照，仍然可读。策略编号显示「已删除」 |
| 多个策略的买入列表有重叠 | 去重，按第一个包含它的策略的排序位置排列 |
