# 技术方案：信号库与基于信号的策略

日期：2026-10-16。状态：草案，待讨论。本文是实施前的方案，不属于 Project Doc 文档库；实施完成后，现状写入 `docs/domains/` 等文档，本文不再维护。

参照对象是 tick-stock-panel（TSP）的信号库与策略文件（`backend/app/strategy/signal_seeds.py`、`custom_signals.py`、`seeds/*.py`），只借鉴其「信号是每只股票每天一个是否」的模型和预置信号清单，不借鉴因子、DSL、评分和 AI 生成策略。

## 1. 目标与范围

目标：在现有均线交叉的基础上，提供一组普通用户看一句话就能理解的预置信号，并让用户用「选买入信号、选卖出信号、设风控」的方式组成策略，在单只股票上回测、在全市场上扫描。

本期做：

- 指标层：均线、EMA、MACD、布林带、N 日最高最低、成交额均值等，计算在 Rust 中。
- 信号库：约 16 个预置信号，分事件型和状态型，每个信号带中文名和一句白话说明。
- 全市场信号扫描：任一信号在某个交易日的命中股票，以及当天所有信号的命中家数。
- 个股与自选股：K 线上标出历史信号，自选股显示当天触发的信号。
- 信号历史表现：信号触发后 N 日的收益分布。
- 策略：买入条件、卖出条件、止损、止盈、最长持有天数；单只股票回测，全市场扫描「今天满足买入条件的股票」。

本期不做：

- 用户自定义表达式或公式（TSP 的「字段 + 运算符 + 阈值」、DSL）。理由见第 10 节。
- 因子、评分排序、IC 检验、参数寻优、因子挖掘。
- 多只股票的组合回测（资金分配、最大持仓数）。第 9 节记录将来需要的改动。
- 盘中信号、监控推送。

## 2. 概念与分层

| 层 | 回答的问题 | 有无状态 | 位置 |
| --- | --- | --- | --- |
| 价格 | 每天的开高低收、成交额是多少 | 无 | `analysis::prices`，SQL 读取 |
| 指标 | 每天的连续数值，例如 20 日均线 | 无 | `analysis::indicators`（新增） |
| 信号 | 每天是否出现了某个情况 | 无 | `analysis::signals`（新增） |
| 策略 | 根据信号和自身持仓，决定买、卖或不动 | 有（持仓、成本、持有天数、现金） | `analysis::strategy`（新增）、`analysis::backtest`（改造） |

约束：同一只股票同一天，指标和信号的结果只取决于截至当天的价格，与查询入口无关。单只股票、全市场扫描、自选股、信号统计和回测共用同一套计算，延续 [ADR：指标在 Rust 中计算](../decisions/indicator_compute.md) 的做法。

信号分两类：

- **事件型（event）**：只在发生那天为真，例如「收盘站上 20 日均线」「MA5 上穿 MA20」。用于买卖时机。
- **状态型（state）**：可以连续多天为真，例如「均线多头排列」「收盘价在 60 日均线上方」。用于过滤条件。

## 3. 价格输入

现有 `prices::closes_between` 只读收盘价。新信号需要开高低收和成交额，新增一个按列存放的结构，替代扫描和自选股里的 `(日期, 收盘价)` 序列：

```rust
/// 一只股票按日期升序的日线，按列存放便于指标计算
pub struct BarSeries {
    pub dates: Vec<NaiveDate>,
    /// 等比前复权价，用于指标和信号
    pub open: Vec<f64>,
    pub high: Vec<f64>,
    pub low: Vec<f64>,
    pub close: Vec<f64>,
    /// 成交额（元），不受送转影响，量能类信号用它
    pub amount: Vec<f64>,
}
```

口径说明：

- 价格用 `mkt.v_stock_bar_qfq` 的等比前复权价，与现有均线一致。
- 量能类信号用成交额，不用成交量。`v_stock_bar_qfq.volume` 是未复权的股数，送转股后股数会突然变大，「放量」会误判；成交额以元计，不受送转影响。
- 全市场读取沿用 `closes_between` 的做法（事务内关闭 JIT、调大 `work_mem`），只是多读几列。读取量大约是现在的 5 倍，耗时需要实测（见第 11 节）。
- 回测仍然需要未复权价成交，继续用 `prices::DailyBar`；两者由同一次查询产出，避免日期错位。

## 4. 指标层

新增 `backend/src/analysis/indicators.rs`，全部是纯函数，输入按日期升序的切片，输出与输入等长的 `Vec<Option<f64>>`，窗口不满时为 `None`：

| 函数 | 说明 |
| --- | --- |
| `sma(values, n)` | 从 `ma.rs` 移过来，保持 Kahan 补偿求和 |
| `ema(values, n)` | 指数移动平均，平滑系数 2 / (n + 1)，第一个值用前 n 根的简单平均作为种子 |
| `macd(close, 12, 26, 9)` | 返回 DIF、DEA、柱（2 × (DIF − DEA)，与国内软件一致） |
| `boll(close, 20, 2.0)` | 中轨为 20 日均线，上下轨为中轨 ± 2 倍总体标准差 |
| `rolling_max(values, n)`、`rolling_min(values, n)` | 单调队列实现，O(n) |

规则：

- 停牌日没有 K 线，不计入窗口，与现有均线口径一致。
- EMA、MACD 依赖初值，越早的数据对当天影响越小但不为零。扫描时只取一段历史，所以全市场扫描与单只股票全历史计算的结果会有极小差异。方案：预热长度取 EMA 周期的 10 倍以上（MACD 取 250 根），并在测试中验证两条路径的信号一致；做不到完全一致的，在领域文档中说明。
- 每个指标声明自己需要的预热根数，信号据此计算所需历史长度。

## 5. 信号库

### 5.1 定义方式

信号在代码中注册，不放进数据库或 YAML，原因是每个信号的计算逻辑不同，用配置表达就要发明一套表达式语言（见第 10 节）。

```rust
pub enum SignalKind { Event, State }

pub struct SignalDef {
    /// 稳定 ID，出现在 URL、策略定义和数据库中，发布后不改名
    pub id: &'static str,
    /// 中文名，例如「站上 20 日均线」
    pub name: &'static str,
    /// 一句白话说明，页面上直接显示
    pub description: &'static str,
    pub kind: SignalKind,
    /// 分组：均线、趋势、突破、量能、涨跌停
    pub group: &'static str,
    /// 方向：看多、看空、中性，只用于页面配色
    pub bias: Bias,
    /// 需要的 K 线根数
    pub warmup: usize,
    /// 对一只股票的全部日线计算每天的结果
    pub compute: fn(&BarSeries) -> Vec<bool>,
}

pub static SIGNALS: &[SignalDef] = &[ /* … */ ];
```

计算结果统一为 `Vec<bool>`，与 `BarSeries` 等长，预热不足的日子为 false。

### 5.2 参数

第一批信号全部是固定参数（例如 MA5、MA20），这样全市场扫描、命中家数、历史统计都可以按信号 ID 缓存，用户也不用理解参数。

现有的可调周期均线交叉保留：`ma_golden`、`ma_death` 两个信号接受 `fast`、`slow` 参数，默认 15、30，范围沿用 `validate_windows`。策略和接口里用 `SignalRef { id, params }` 引用信号，只有声明了参数的信号才接受 `params`。

### 5.3 交叉判定

所有「上穿」「下穿」「站上」「跌破」都用同一个函数，从 `ma::cross_signals` 推广而来：比较两条序列（或一条序列和一个常数），用相对差和 1e-9 容差确定 +1、0、−1 状态，从上一个非零状态翻转时才算交叉。

这一点与 TSP 不同。TSP 写成「今天 A > B 并且昨天 A ≤ B」，在一字板、长期价格不变时会出现假交叉，[均线与交叉信号](../domains/ma_signals.md#cross_rule) 记录过实测的影响。

### 5.4 第一批信号

| ID | 名称 | 类型 | 规则 |
| --- | --- | --- | --- |
| `ma_golden` | 均线金叉 | 事件 | 快线上穿慢线，默认 15、30，可调 |
| `ma_death` | 均线死叉 | 事件 | 快线下穿慢线，默认 15、30，可调 |
| `ma5_cross_ma20_up` | MA5 上穿 MA20 | 事件 | 短线转强 |
| `ma5_cross_ma20_down` | MA5 下穿 MA20 | 事件 | 短线转弱 |
| `ma20_cross_ma60_up` | MA20 上穿 MA60 | 事件 | 中线转强 |
| `close_cross_ma20_up` | 站上 20 日均线 | 事件 | 收盘价从 MA20 下方到上方 |
| `close_cross_ma20_down` | 跌破 20 日均线 | 事件 | 收盘价从 MA20 上方到下方 |
| `macd_golden` | MACD 金叉 | 事件 | DIF 上穿 DEA |
| `macd_death` | MACD 死叉 | 事件 | DIF 下穿 DEA |
| `boll_break_upper` | 突破布林上轨 | 事件 | 收盘价上穿上轨 |
| `boll_break_lower` | 跌破布林下轨 | 事件 | 收盘价下穿下轨 |
| `new_high_60` | 创 60 日新高 | 事件 | 收盘价高于此前 60 根 K 线的最高收盘价 |
| `new_low_60` | 创 60 日新低 | 事件 | 收盘价低于此前 60 根 K 线的最低收盘价 |
| `amount_surge` | 放量 | 事件 | 成交额大于此前 5 日平均成交额的 2 倍 |
| `ma_bullish` | 均线多头排列 | 状态 | MA5 > MA10 > MA20 > MA60 |
| `above_ma60` | 在 60 日均线上方 | 状态 | 收盘价高于 MA60 |

60 日新高新低用收盘价而不是最高最低价，原因是收盘价更稳定，也与其他信号的价格基础一致；如果希望与看盘软件的「新高」一致，可以改成最高价，需在评审时确定。

### 5.5 涨跌停类信号（第二阶段）

涨停、连板、炸板对 A 股用户很直观，但不建议像 TSP 那样自己算涨停价：

- 涨跌幅限制随板块（主板 10%、创业板和科创板 20%、北交所 30%）、ST、上市初期不设限而不同。
- 涨停价以交易所前收盘价为基准，`mkt.stock_bar_1d.pre_close` 只有快照写入的日子才有，历史数据为空；除权日的前收还要按交易所规则调整。

方案：用已同步的供应商数据。`special.limit_up_pool`（2020-07-22 起）提供涨停和连板天数，`special.limit_break_pool` 提供炸板（只有最近一年）。信号从 `raw.record` 读取，覆盖范围以外的日期返回「无数据」而不是 false，页面上注明起始日期。payload 字段名需要先查样本确认（待确认）。

如果之后需要在回测中使用，再考虑为它们增加类型化表（`AGENTS.md`：只有需要类型化表时才在 `sinks.rs` 增加投影）。

## 6. 计算、缓存与存储

### 6.1 全市场扫描

现有 `ScanCache` 按 (交易日, 快线, 慢线) 缓存均线交叉结果。改为：

- 一次扫描对每只股票计算全部固定参数信号，结果是 `交易日 → { 信号 ID → 命中股票列表 }`，同时得到每个信号的命中家数。
- 缓存键为交易日，版本仍是 `ops.derived_version` 中 `adj_factor` 的 `updated_at`。
- 可调参数的 `ma_golden`、`ma_death` 保持现有的 (交易日, 快线, 慢线) 缓存。
- 读取范围取所有信号 `warmup` 的最大值，加上停牌余量，换算为自然日。

### 6.2 单只股票

按需计算全历史，不缓存。现有单只股票全历史均线是 5 到 11 毫秒，加上全部信号后需要实测。

### 6.3 信号历史表现

统计某个信号在全市场历史上触发后 5、10、20 个交易日的收益：平均值、中位数、上涨比例、样本数，并与同期全部股票的平均收益对比。

- 收益口径：触发日次日开盘价进场，第 N 个交易日收盘价计算，用前复权价，不含费用。
- 局限：样本之间持有期重叠，不是可成交的策略收益；只用本地已有日线，回补未完成时样本偏少；包含退市股票但退市后的收益缺失（在页面说明）。
- 计算量：需要读取全市场全部历史，第一次计算预计在秒级以上（待实测）。先按 (信号, 版本) 缓存在进程内；如果实测超过 10 秒，再在复权重算完成后把信号事件物化到表里（见 6.4）。

### 6.4 是否物化信号

第一阶段不物化，全部按需计算加进程内缓存。[ADR：指标在 Rust 中计算](../decisions/indicator_compute.md) 否决物化均线，理由是周期由用户输入、组合太多；固定参数的信号没有这个问题，所以物化是可选项。

如果需要物化，新增迁移：

```sql
-- 预置信号的触发记录，复权因子重算完成后全量重算
CREATE TABLE mkt.signal_event (
  signal_id  TEXT NOT NULL,
  trade_date DATE NOT NULL,
  thscode    TEXT NOT NULL,
  PRIMARY KEY (signal_id, trade_date, thscode)
);
CREATE INDEX signal_event_code_idx ON mkt.signal_event (thscode, trade_date);
```

只存事件型信号，状态型信号连续为真，行数太多。重算挂在 [运行结束后的计算](../architecture/sync_pipeline.md#postprocess) 中复权重算之后，完成后更新 `ops.derived_version` 新增的 `signal_event` 行。是否需要，等第一阶段实测后决定，并单独写 ADR。

## 7. 策略

### 7.1 定义

```rust
pub struct StrategySpec {
    /// 买入：这些事件信号中任意一个发生
    pub entry_any: Vec<SignalRef>,
    /// 买入过滤：这些状态信号必须同时为真，可以为空
    pub entry_filters: Vec<SignalRef>,
    /// 卖出：这些事件信号中任意一个发生，可以为空
    pub exit_any: Vec<SignalRef>,
    /// 止损：收盘价相对买入价下跌达到这个比例时卖出，例如 0.08
    pub stop_loss: Option<f64>,
    /// 止盈：收盘价相对买入价上涨达到这个比例时卖出
    pub take_profit: Option<f64>,
    /// 持有达到这么多个交易日时卖出
    pub max_hold_days: Option<u32>,
}
```

刻意不提供「信号 A 和信号 B 同一天都发生」：两个事件同一天发生的概率很低，用户很容易配出一个永远不触发的策略。需要组合时，用「一个事件 + 若干状态过滤」表达，例如「MACD 金叉，且在 60 日均线上方」。

校验：`entry_any` 不能为空；`exit_any` 与止损、止盈、最长持有天数至少要有一个，否则买入后永远不卖；`entry_any`、`exit_any` 只能放事件型，`entry_filters` 只能放状态型；比例在 0 到 1 之间，持有天数在 1 到 250 之间。

### 7.2 预置策略

策略在代码中预置几个，用户可以复制后修改：

| 名称 | 买入 | 过滤 | 卖出 | 风控 |
| --- | --- | --- | --- | --- |
| 均线金叉（现有回测） | `ma_golden(15, 30)` | 无 | `ma_death(15, 30)` | 无 |
| 短线转强 | `ma5_cross_ma20_up` | `above_ma60` | `ma5_cross_ma20_down` | 止损 8% |
| 突破新高 | `new_high_60` | `ma_bullish` | `close_cross_ma20_down` | 止损 8%，最长 40 天 |
| MACD 金叉 | `macd_golden` | `above_ma60` | `macd_death` | 止损 8% |

止损比例和持有天数是示例值，没有回测依据，评审时可以调整，页面上不作为推荐参数。

「均线金叉」与现有 `GET /backtest/ma-cross` 的规则完全相同，作为改造前后结果一致的基准（见第 11 节）。

### 7.3 用户策略的保存

新增迁移，保存用户在网页上建的策略：

```sql
-- 用户在网页上建的策略。spec 是 StrategySpec 的 JSON，读取时按当前代码校验
CREATE TABLE app.strategy (
  id         BIGSERIAL PRIMARY KEY,
  name       TEXT NOT NULL,
  spec       JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

信号 ID 发布后不改名。将来删除某个信号时，引用它的策略在读取时校验失败，页面显示「策略引用的信号已不存在」，不静默跳过。

### 7.4 回测改造

`backtest::run` 目前直接调用 `ma_cross`，在收盘后根据金叉、死叉下单。改造为：

1. 先由 `StrategySpec` 和 `BarSeries` 算出两个 `Vec<bool>`：`entry`（任一买入事件且全部过滤为真）、`exit_signal`（任一卖出事件）。这一步在 `analysis::strategy` 中，是纯函数。
2. `run` 接收这两个向量和风控参数，其余逻辑不变：次日开盘成交、每手 100 股、一字板顺延、反向信号取消挂单、分红送转、交易成本。
3. 收盘后的判断顺序：持仓时依次检查止损、止盈、最长持有天数、卖出信号，任一满足就挂次日开盘的卖单；空仓时检查买入信号。

风控规则的口径：

- 止损和止盈按收盘价判断，次日开盘卖出，不模拟盘中触价成交。跳空低开时实际亏损会超过止损比例，这与只有日线时的真实情况一致，在领域文档中说明。
- 比较用前复权价，除权日不会误触发止损。
- 买入价用前复权的成交价，持仓期间除权后仍可比较。
- 持有天数按交易日计算，停牌日不计。

`Summary` 新增 `exit_reasons`：按卖出原因（信号、止损、止盈、到期）统计的笔数，`Trade` 新增 `exit_reason`，方便用户理解每笔为什么卖出。

### 7.5 策略扫描

「今天哪些股票满足买入条件」直接复用 6.1 的全市场信号结果：对 `entry_any` 求并集，再与 `entry_filters` 求交集。状态型信号也需要在扫描中保留当天的命中列表。

## 8. 接口

新增和变更（路径都在 `/api/v1` 下）：

| 方法与路径 | 说明 |
| --- | --- |
| `GET /signals` | 信号目录：ID、名称、说明、类型、分组、方向、可调参数 |
| `GET /signals/summary` | 某个交易日每个信号的命中家数，`date` 默认最新交易日 |
| `GET /signals/{signal_id}/hits` | 某个交易日命中某个信号的股票；可调参数的信号接受 `fast`、`slow` |
| `GET /signals/{signal_id}/stats` | 信号历史表现，`horizons` 默认 5、10、20 |
| `GET /securities/{thscode}/signals` | 一只股票在区间内触发的信号，`ids` 过滤，`start`、`end` |
| `GET /strategies/presets` | 预置策略 |
| `GET`、`POST /strategies`，`GET`、`PUT`、`DELETE /strategies/{id}` | 用户策略的增删改查 |
| `POST /backtest` | 按 `StrategySpec` 回测单只股票，请求体含 `thscode`、`spec`、区间、资金、成本；响应与现有回测相同，另加卖出原因 |
| `GET /strategies/{id}/scan`、`POST /strategies/scan` | 某个交易日满足买入条件的股票，前者用已保存策略，后者用请求体中的策略 |

保留并标为兼容：

- `GET /signals/ma-cross`：改为调用 `ma_golden`、`ma_death`，响应不变。
- `GET /backtest/ma-cross`：改为调用预置策略「均线金叉」，响应不变，另加 `exit_reasons`。
- `GET /watchlist`：`diagnosis` 新增 `signals_today`（当天触发的信号 ID 列表），其余字段不变。

回测改用 `POST` 是因为策略定义是嵌套结构，放在查询参数里难以表达和校验。

每个响应都要写 `description`（`AGENTS.md` 要求，否则前端生成客户端失败）。用户策略的名称和 JSON 一律走绑定参数。

安全说明：服务目前没有登录（见 [ADR：CI 构建镜像，部署只交付服务本身](../decisions/ci_cd.md)），新增的策略写接口与自选股一样，任何能访问端口的人都能增删。这与现状一致，但可写数据变多了，部署说明中应再次提醒只在可信网络中暴露端口。

## 10. 关键取舍

- **预置信号，不开放表达式。** TSP 允许用户用「字段 + 运算符 + 阈值 + 天数偏移」组合信号，灵活但正是理解成本的来源：用户要知道有哪些字段、偏移是什么意思、交叉要写成两个条件。预置信号覆盖常见需求，后续按用户反馈增加。代价是用户不能自己造信号，需要新信号时要改代码。是否以及何时开放，留到第一批上线之后再评估。
- **事件和状态分开。** 买卖时机只能选事件，过滤只能选状态，从界面上避免「永远不触发」和「每天都触发」两类配置错误。
- **不做评分和排序。** 扫描结果按代码排序，只回答「满足或不满足」。排序需要因子，理解成本高，也容易让人误以为排在前面的更好。
- **不做组合回测。** 单只股票回测足够回答「这个策略在这只股票上表现如何」。组合回测需要资金分配、同日多只触发时的选择规则、最大持仓数，而选择规则又会引出排序。等单只股票的策略稳定后再评估，届时 `backtest::run` 需要从单一持仓改为多持仓账本。
- **TSP 的引擎不复用。** TSP 是 Python、Polars、Parquet，与本项目的 Rust、PostgreSQL 不兼容；只借鉴信号清单和概念。

## 11. 测试与验证

- 指标单元测试：每个指标与逐项直接计算的结果比较，沿用 `sma_matches_direct_average` 的写法；EMA、MACD、布林带用手算的小序列核对，并与同花顺软件抽查几只股票的数值（人工，记录在 PR 中）。
- 信号单元测试：每个信号至少覆盖触发、不触发、预热不足、价格相等不产生假交叉四种情况。
- 一致性测试：同一只股票，全市场扫描路径和单只股票全历史路径在最近 N 个交易日的信号完全一致；不一致的信号（如果 EMA 预热不足导致）必须在测试中显式列出并在文档中说明。
- 回测回归测试：预置策略「均线金叉」与改造前 `GET /backtest/ma-cross` 在现有三个单元测试和若干真实股票上的交易记录、汇总指标逐项相同。实施第一步先把改造前的结果存为测试基线。
- 风控测试：止损、止盈、到期分别触发；除权日不误触发止损；止损与卖出信号同一天时只挂一次卖单。
- 集成测试：新接口的参数校验和错误响应，使用 `NIULAI_TEST_DATABASE_URL`。
- 性能实测：在约 1,500 万行日线的库上测全市场扫描第一次耗时、命中缓存耗时、单只股票全部信号耗时、信号历史统计耗时。目标是全市场扫描第一次在 2 秒内、单只股票在 50 毫秒内；这是目标，不是已验证的结果，超出时再决定是否物化（6.4）。
