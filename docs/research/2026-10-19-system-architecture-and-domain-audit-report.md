# niulai 系统架构与金融业务模型全面审计报告

日期：2026-10-19
状态：完成
归档路径：`docs/research/2026-10-19-system-architecture-and-domain-audit-report.md`

## 1. 审计概貌与核心结论

本项目是一套基于 Rust（Axum + SQLx + Tokio）后端与 React 前端的 A 股股票及交易所 ETF 诊断工作台。工程实现具有很高的规范度：代码整洁、强类型约束、文档库（Project Doc）完备且无编译警告。

但在深入代码细节与运行机制后，系统在**底层软件架构**与**金融量化内核**两个层面存在显著的隐患与设计妥协：
1. **软件工程层面**：存在典型的数据层反向依赖业务层（循环耦合）、PostgreSQL 连接池容量倒挂与饥饿风险、Tokio 异步运行时混部 CPU 密集计算引发的调度抖动，以及非等值区间连接导致的查询内存补丁。
2. **金融业务层面**：回测系统存在理想化撮合（0 滑点、次日开盘全额成交）、缺乏移动止盈（Trailing Stop）风控、单股回测与全市场回测口径双轨制，以及实盘人肉记账的高摩擦。

本报告对会话中审查出的全部问题进行完整归纳、机理剖析并给出对应的改进方案与落地路线。

## 2. 软件工程与系统架构问题

### 2.1 架构分层倒置与循环依赖（严重级别：P0）

#### 现象与代码位置
- `backend/src/sync/executor.rs` 的 `after_task` 在波次完成时，直接在底层数据管道内调用顶层业务：`crate::analysis::screener::run_and_store`（每日巡检）与 `crate::advice::refresh_all`（生成调仓建议）。
- `backend/src/sync/executor.rs` 的 `maintain` 定期维护循环中，直接调用了 `crate::advice::maintain`。
- `backend/src/sync/mod.rs` 的 `Engine::new` 构造函数中，混入了 `crate::auth::init_first_admin`（初始化管理员）与 `crate::analysis::screener::sync_builtin_strategies`（内置策略同步）。
- `backend/src/advice/inputs.rs` 反向调用了 `crate::sync::audit::core_backfill_left`；`backend/src/advice/mod.rs` 反向调用了 `crate::sync::scheduler::claim`。

#### 根因剖析
违背了整洁架构（Clean Architecture）的依赖倒置原则。数据摄取流水线（`sync`）本应属于通用基础设施和数据流底层，却直接硬编码感知了上层的选股策略、账户建议与用户鉴权逻辑。同时上层业务反向刺穿底层内部状态，形成双向循环依赖，导致 `sync` 无法独立抽离、单独测试或作为纯粹数据通道复用。

#### 建议方案
- **引入进程内领域事件（Domain Event）**：定义 `DomainEvent::SyncBatchCompleted` 与 `DomainEvent::MaintenanceTick`，`sync` 模块只负责拉取数据、落库并发射事件，彻底删除所有对 `analysis` 和 `advice` 的直接调用。
- **应用层统一编排**：由 `server.rs` 或独立的协调器（Coordinator）订阅领域事件，异步调度后置的巡检和建议计算。
- **清理启动副作用**：将管理员初始化与策略模板同步移至全局启动引导（`bootstrap`），纯化 `Engine::new`。

### 2.2 PostgreSQL 连接池饥饿风险（严重级别：P0）

#### 现象与代码位置
- `backend/src/config.rs` 中 `default_db_max_connections` 默认为 10，连接获取超时仅为 10 秒（`acquire_timeout = 10s`，见 `backend/src/db.rs`）。
- 全局单一连接池由所有组件共享。

#### 根因剖析
并发消费者与连接池上限严重倒挂：
- 数据同步执行器（Worker）：并发数为 3，常态占用 3 个连接；
- 全市场日线扫描信号量：`SCAN_SLOTS` 为 2，`BACKGROUND_SLOT` 为 1，扫描期间分 40 个批次连续申请事务；
- 调度器与租约维持循环：占用 1~2 个连接；
- 此时仅剩 1~2 个连接可供 Axum Web API 使用。当前端单次打开页面并发请求自选股、大盘环境、持仓诊断时，极易因拿不到连接触发 `PoolTimedOut`，导致前端页面大面积报错 500。

#### 建议方案
- **上调默认池容量**：将默认连接上限提升至 32~50。
- **实施动静双池隔离（Dual Pool）**：
  - `api_pool`（交互式连接池）：配额约占 60%，专门保障 Web HTTP 请求秒级响应；
  - `batch_pool`（批处理连接池）：配额约占 40%，专供数据同步、大范围批次扫描与后台计算。

---

### 2.3 Tokio 异步运行时与 CPU 密集计算混部（严重级别：P1）

#### 现象与代码位置
- `backend/src/analysis/prices.rs` 的 `for_each_stock` 在 5000 只股票的大循环中，对每只股票调用 `run_cpu(|| f(code, bars))`，其内部使用 `tokio::task::block_in_place`。
- `backend/src/analysis/portfolio.rs` 中组合回测完成数据拉取后的逐日模拟、持仓排序、净值推算等逻辑，直接裸跑在异步线程上。

#### 根因剖析
- Tokio 多线程运行时专为非阻塞 I/O 设计。在 5000 次遍历循环中高频触发 `block_in_place`，会导致工作线程反复挂起唤醒并引发跨线程任务窃取，带来巨大的上下文切换损耗。
- `portfolio.rs` 内的百万次交易规则迭代未移出异步主循环，会长时间霸占 Tokio 工作线程，导致当前线程上排队等待的网络 I/O 请求严重饥饿，表现为全市场回测期间 Web 接口请求卡顿。

#### 建议方案
- 严格分离 I/O 运行时与计算线程池，耗时的日线迭代与回测模拟整体封装至 `tokio::task::spawn_blocking` 或专用的 `rayon` 线程池中执行。
- 在批次读取完成后一次性进入密集计算，禁止在批次内部的元素细粒度循环中高频切换上下文。

---

### 2.4 非等值区间 Join 依赖大内存查询补丁（严重级别：P1）

#### 现象与代码位置
- `backend/src/analysis/prices.rs` 中查询前复权日线时使用区间连接：
  `mkt.stock_bar_1d b LEFT JOIN mkt.adj_segment s ON s.thscode = b.thscode AND b.trade_date >= s.valid_from AND b.trade_date < s.valid_to`。
- 查询前必须执行 `SET LOCAL jit = off` 与 `SET LOCAL work_mem = '128MB'`。

#### 根因剖析
关系型数据库对基于不等式的范围连接（Non-equi Join）难以使用高效的哈希关联算法。随着日线数据累积至数千万行，优化器易误判基数并选择高代价扫描计划。系统不得不通过强制关闭 JIT 并分配高达 128MB 的单事务内存来进行规避。

#### 建议方案
- 将复权因子按交易日直接等值物化，或在全市场扫描前批量拉取当前区间的 `adj_segment`，在 Rust 内存中通过二分查找完成价格计算。
- 消除单次扫描中对超大工作内存 `work_mem = 128MB` 的强依赖，减轻数据库并发内存抖动。

---

### 2.5 单一供应商强绑定与缺乏抽象（严重级别：P2）

#### 现象与代码位置
- `backend/src/vendor/` 仅有 `hithink.rs`；
- `datasets.yaml` 与同步框架深度嵌入了同花顺私有的错误码体系（例如 `empty_codes: [1001, 3001]`）、URL 协议与 Token 规范。

#### 根因剖析
缺乏通用的行情数据源抽象层（Data Source Abstraction）。一旦供应商接口调整、权限受限或需要引入补充源（如 AkShare、Tushare、本地离线数据），无法平滑扩展。

#### 建议方案
- 提炼 `trait DataSourceClient: Send + Sync`，标准化数据抓取、频率控制与错误分类接口。
- 将具体供应商私有逻辑隔离在特定客户端实现内部，使同步引擎只依赖通用抽象。

---

### 2.6 进程故障隔离粗粒度（严重级别：P2）

#### 现象与代码位置
- `backend/src/server.rs` 中的 `serve` 函数将 API、Worker、Scheduler 汇聚在同一个 `JoinSet` 中，一旦任何一个子组件返回错误或 Panic，整个服务立刻关闭退出。

#### 根因剖析
将多项异构职责打包在单进程中虽降低了部署复杂度，但缺乏故障防护隔板（Bulkhead Pattern）。单个复杂的组合回测或异常脏数据导致的 Panic，会导致前台 Web 控制台瞬间不可用。

#### 建议方案
- 对后台执行器和非关键定时任务增加 `std::panic::AssertUnwindSafe` 捕获隔离，单个任务计算失败记录日志并丢弃，避免连锁引发整站宕机。

## 3. 金融量化与业务模型问题

### 3.1 理想化撮合模型与买入真实性缺失（严重级别：P0）

#### 现象与影响
- 回测引擎（`backend/src/analysis/backtest.rs`、`portfolio.rs`）假定信号触发后次日一律按开盘价（Open）100% 撮合，且默认滑点为 0。
- 仅用「最高价等于最低价且涨停」的一字板判定无法成交。

#### 风险分析
在真实 A 股市场中，出现强烈突破信号或强势连板形态的标的，次日开盘往往大幅高开抢筹，甚至开盘数分钟内封死涨停。回测在开盘价无摩擦撮合，会导致短线动量策略在回测中产生严重的「纸面繁荣」，而在实盘中根本买不进或者由于追高滑点严重亏损。

#### 建议方案
- 在回测参数中引入显式滑点设定（如默认双边各 0.2%~0.3% 摩擦成本）。
- 增加高开幅度限制（如次日开盘高开超过 4% 视为放弃买入或提高成交价）。

---

### 3.2 卖出风控机制单一，缺少移动止盈（Trailing Stop）（严重级别：P0）

#### 现象与影响
- 策略卖出规则（`backend/src/analysis/strategy.rs`）仅支持：固定止损、固定止盈、最大持有天数、反向信号。
- 缺乏自持仓最高盈利回撤的动态止盈保护。

#### 风险分析
A 股个股波动剧烈，若买入后股票大幅冲高 25%（未触及 30% 静态止盈目标），随后跟随大盘走弱阴跌；由于止损线设定在买入成本价下方 8%，系统会眼睁睁看着利润全部回吐并转为亏损。这是缺乏金融背景的散户在实盘中最容易产生严重心态崩溃的场景。

#### 建议方案
- 在策略的 `exit` 规则中增加移动止盈（Trailing Stop）逻辑：记录持仓以来的前复权最高价，当最高涨幅超过阈值（如 10%）且从最高点回撤超过设定比例（如 6%）时，强制止盈离场。

---

### 3.3 回测与巡检口径双轨制（严重级别：P1）

#### 现象与影响
- **单股回测 vs 全市场组合回测**：单股回测采用未复权价格成交、真实分红送转事件精确记账、按一手 100 股取整；全市场组合回测采用前复权价格连乘近似再投资、允许零股交易。
- **强势板块过滤失效**：每日巡检支持板块强势过滤，但组合回测硬编码禁用了该过滤（由于板块成分缺乏历史时序快照）。

#### 风险分析
同一套策略在单股详情页、组合回测页和每日巡检页计算出的买卖点和收益表现不一致，破坏了量化系统最重要的逻辑自洽性。

#### 建议方案
- 在页面和文档中显式标注口径边界。
- 长期推进板块成分股的历史时序沉淀，使组合回测具备回溯板块强度的能力。

---

### 3.4 历史回测中的幸存者偏差与退市盲区（严重级别：P1）

#### 现象与影响
- 基础代码表主要覆盖当前存续证券，缺乏已退市股票的历史日线数据。

#### 风险分析
回测运行在历史区间时，天然规避了所有历史上因重大违规、造假或经营失败而退市归零的股票，导致策略全市场基准与胜率系统性虚高。

#### 建议方案
- 明确标注回测数据范围具备幸存者偏差。
- 建议将选股与投资组合研究的重心逐步向不易退市、无造假风险、免印花税的行业与宽基 ETF 倾斜。

---

### 3.5 启发式投票机制与调仓建议的人肉记账摩擦（严重级别：P1）

#### 现象与影响
- `backend/src/account/rules.rs` 与 `backend/src/advice/generate.rs` 依靠「命中策略数从多到少」对候选标的进行排序。
- 账户持仓与流水依赖用户每日在前端手动确认「已执行」或手工补录。

#### 风险分析
- 技术指标策略往往具有很高的同质性（例如多个趋势策略同时选出近期暴涨的高风险妖股），简单依靠多数票排序无法起到多策略风险分散的作用，反而会加剧仓位向高波动个股集中。
- 实盘交易缺乏自动对账，一旦散户连续数日未进入系统打卡，账本失真会导致后续所有调仓建议失效。

#### 建议方案
- 强化账户持仓的「一键快照覆盖对齐」功能，降低补录成本。
- 在候选推荐中增加流动性、波动率与行业分散度惩罚，避免单一极端板块被过度推选。

---

## 4. 优先级建议与实施路线图

```text
阶段一：底层架构与稳定性加固（立即实施）
  ├─ 1. 拆解循环依赖：引入 Domain Event 总线，解耦 sync、analysis 与 advice
  ├─ 2. 改造数据库连接池：提升连接上限，实现 API 与 Batch 双池隔离，杜绝 500 超时
  └─ 3. 隔离 CPU 计算：将组合回测与扫描计算移入 spawn_blocking / 专用线程池

阶段二：交易真实性与风控防护（产品与算法跟进）
  ├─ 1. 策略引擎增加移动止盈（Trailing Stop）风控机制
  ├─ 2. 回测增加滑点成本与高开限制，剔除纸面虚假繁荣
  └─ 3. 强化持仓快照校准体验，降低个人使用维护摩擦
```
