# 交接说明：指标、信号、策略的梳理与改造方向

> 调研笔记，不属于 Project Doc 文档库。记录 2026-10-16 的讨论结论，交给后续实现使用。

## 0. 给执行者的前置要求

- 先按仓库 `AGENTS.md` 的 Project Doc gate 加载 `project-doc` skill，完整阅读 `docs/index.md`。
- 动手前阅读：
  - `docs/domains/strategies.md`：指标、信号、策略定义、巡检、诊断
  - `docs/domains/backtest.md`

  - `docs/decisions/indicator_compute.md`
  - `docs/research/2026-10-16-signal-library-and-strategy-plan.md`：之前的方案，含「信号历史表现」「是否物化信号」的规划
- 仓库约定（摘自 `AGENTS.md`）：
  - 已执行的迁移文件不能改，表结构变更一律新增迁移。
  - 每个 `#[utoipa::path]` 响应都要写 `description`。
  - 所有 `ToSchema` 类型名在整个 API 中必须唯一。
  - 后端接口改动后，在 `frontend/` 下执行 `pnpm api:spec && pnpm api:gen && pnpm typecheck`。
  - 提交前：后端 `cargo clippy --all-targets` 无警告、`cargo test` 通过；前端 `pnpm typecheck`、`pnpm lint`、`pnpm test` 全部通过。

- 改代码时同步维护文档。推翻旧决策要写新 ADR，并把旧决策标为 `superseded`。

## 1. 起因（用户提出的问题）

1. 信号全部内置，但没有一个地方完整展示信号的详情和定义，露出的信息太少。希望有一个单独的信号表格，把每个信号的定义和含义解释清楚。
2. 信号需要抽象，方便以后自定义。
3. 策略应该有买点和卖点，是建在信号之上的一层。现在看不到买卖点，策略和信号的边界也不清楚。
4. 指标只在说明页简单提了一下，看不出有哪些、怎么用、和信号策略是什么关系，整条链路接不上。
5. 根本问题：这些都藏在服务内部，用户不知道有什么数据，也就不知道这些数据能怎么用。

## 2. 现状（已核实的事实）

### 2.1 代码位置

| 层 | 文件 | 内容 |
| --- | --- | --- |
| 指标 | `backend/src/analysis/indicators.rs` | `CATALOG` 共 29 个，分 8 组：价格、量能、均线、MACD、超买超卖、波动、动量、区间。`Frame::compute()` 计算，返回与日线等长的 `Vec<f64>`，带缓存 |
| 信号 | `backend/src/analysis/signals.rs` | `SignalId` 枚举共 25 个，分 7 组：均线、MACD、超买超卖、突破、量能、K 线形态、涨跌停。`compute()` 是一个大 `match`，返回 `Vec<bool>` |
| 策略 | `backend/src/analysis/strategy.rs` | `Definition`（JSON，存在 `app.strategy.definition`）：`universe` 股票池、`all` / `any` 买入条件、`exit` 卖出规则、`sort`、`limit`。条件只有 `Signal`、`Compare` 两种 |
| 巡检 | `backend/src/analysis/screener.rs` | 只输出「今天满足买入条件的股票」，写入 `app.screen_run`、`app.screen_hit` |
| 诊断 | `backend/src/analysis/diagnosis.rs` | 趋势、动量、量能、位置四个维度，指标和阈值写死在代码里 |
| 回测 | `backend/src/analysis/backtest.rs`、`portfolio.rs` | 单只股票回测、全市场组合回测。卖出规则只在这里生效 |
| 接口 | `backend/src/api/strategy.rs` | `GET /api/v1/strategies/catalog` 一次返回指标、信号、模板、默认股票池 |
| 前端 | `frontend/src/pages/GuidePage.tsx` | 路由 `/guide`，导航名「说明」，分「信号」「指标」两个 tab |

### 2.2 已经做到的

- 三层的依赖方向在代码里是干净的：策略依赖信号，信号依赖指标。
- 指标和信号的元数据完整：都有 `name`、`group`、`description`、`usage`。信号还有 `tone`（偏多 / 偏空）、`kind`（事件 / 状态）和参数范围。单元测试会检查每条都写了说明。
- 说明页已经展示了全部指标和信号的说明。信号条目有「今天哪些股票出现了」和「用它新建策略」两个按钮。
- 每条条件都能转换成白话描述（`Condition::describe()`）。

注意：讨论中一度说「前端没有指标展示」，这个说法有误，已更正。说明页里有指标，问题是信息不够，链路也不通。

### 2.3 存在的问题

1. 指标只讲了「是什么」，没讲「能用在哪、怎么用」：
   - 实际用在 4 个地方：策略的比较条件、策略排序、信号的原料、个股诊断。说明页一个都没讲。
   - 没有「在策略里可以怎么写」的示例。
   - 常用阈值（RSI 70/30、量比 1.5/0.7 等）只散落在 `usage` 文字里，没有结构化。
   - MACD（12/26/9）、KDJ（9/3/3）、布林带（20 日、2 倍标准差）的固定参数没有展示。
   - 指标条目没有任何操作入口。
2. 信号和指标之间的关系看不到：信号用了哪些指标，只写在 `signals.rs` 的 `compute()` 里。
3. 信号是硬编码的：新增信号必须改 Rust 代码、重新编译。和策略是 JSON 定义的做法正好相反。
4. 策略的买卖点不清楚：
   - `exit` 卖出规则只在回测中生效，每日巡检不用。
   - 巡检只给出「今天入选」，不给卖点，也不跟踪入选之后的状态。
5. 诊断的规则写死，卡片只显示结论，不显示依据是哪个指标。
6. 数据层完全不可见：`backend/config/datasets.yaml` 同步了估值、财务、涨停池、龙虎榜、热股等 30 多个数据集，但指标层只用了日线。没有地方能看到「库里有什么数据」。
7. 未核实：个股 K 线页能否叠加显示指标，代码还没看。

## 3. 达成一致的概念分层

最终定稿：

> 数据提供行情；指标负责计算；信号负责识别事件或状态；策略用信号和指标定义买点和卖点；回测负责把买卖点换成成交，并统计收益。

| 层 | 输入 | 输出 | 不负责 |
| --- | --- | --- | --- |
| 数据 | 同花顺接口 | 日线（前复权） | — |
| 指标 | 日线 | 每天一个数（例：RSI = 65.3） | — |
| 信号 | 指标 | 每天是 / 否（例：今天 RSI 是否上穿 30） | — |
| 策略 | 信号、指标 | 每只股票的买点和卖点 | 资金、仓位、同时持有几只 |
| 回测 | 买卖点 | 成交、成本、收益 | 决定什么时候买卖 |

讨论中纠正过的两个误解：

- 指标不等于原始数据。原始数据是同花顺同步来的日线和复权事件；指标是在日线上算出来的。29 个指标里只有开高低收、成交量、成交额 6 个基本等于原始值。
- 信号不是「动态计算的指标」。指标和信号都是现算的，不存库。区别在输出：指标是数，信号是是 / 否。

## 4. 已做的决定

| 编号 | 决定 | 说明 |
| --- | --- | --- |
| D1 | 采用第 3 节的五层分层 | 数据、指标、信号、策略、回测 |
| D2 | 策略只基于技术面，现在不做持仓和资金管理 | 用户明确要求 |
| D3 | 资金和组合参数不进入策略定义 | `capital`、`max_positions`、等额分配继续作为组合回测参数 |
| D4 | 止损、止盈、最长持有天数留在策略里 | 只依赖单只股票自己的买入价和持有天数，不依赖资金，仍算技术面规则 |
| D5 | 卖点按单只股票的状态机计算，不需要账户 | 空仓时出现买点就变成持有；持有时触发卖出规则就回到空仓。和现有单只股票回测逻辑一致 |
| D6 | 每层都要露出来，回答四个问题 | 有哪些（目录）、是什么（定义和口径）、从哪来（用了上一层的什么）、被谁用（下一层哪些东西用到它） |
| D7 | 信号抽象成可定义的结构，为以后自定义做准备 | 用户的原始需求。方案见 5.3，细节待确认 |
| D8 | 接入估值、财务等非行情数据先搁置 | 只做技术面，随 D2 一起定 |

## 5. 改造方案

### 5.1 数据层：新增露出

新增「数据」目录。每个数据集展示：名称、来源接口、更新频率、覆盖范围（起始日期、股票数、最新日期）、主要字段、被哪些指标使用（没用到的标「未接入」）。只做技术面时，重点讲清楚日线和复权，其余数据集先只做展示。

### 5.2 指标层：补上来源和用法

在现有 `IndicatorInfo` 上补充：

- 输入：用了哪些原始字段，例如「前复权收盘价」。
- 公式和固定参数：例如 MACD 写明 12/26/9。
- 常用阈值：结构化数据，例如 RSI `[30, 70]`，供页面展示，也供编辑器点选。
- 示例条件：例如「RSI（14）低于 30」「相对 20 日均线偏离在 −2% 到 2% 之间」。
- 被谁用：哪些信号、哪些策略、诊断的哪个维度。
- 可选：在一只股票的 K 线上画出来；查看今天全市场的分布。

### 5.3 信号层：独立成页，改成规则定义

信号定义从「`match` 里的一个分支」改成「规则类型 + 指标 + 参数」。建议的规则类型：

| 规则类型 | 含义 | 覆盖的现有信号 |
| --- | --- | --- |
| 上穿 / 下穿（A，B） | 指标 A 穿过指标 B | 均线金叉死叉、MACD 金叉死叉、KDJ 金叉死叉、收盘站上或跌破均线、布林带上下轨突破（10 个） |
| 越过阈值（A，水平，方向） | 指标穿过一个固定值 | MACD 上穿零轴、RSI 走出超卖、RSI 进入超买（3 个） |
| 比较（多条同时满足） | 满足期间每天为真 | 放量、均线多头排列、均线空头排列（3 个） |
| 区间极值（A，N） | 创 N 日新高或新低 | 新高、新低（2 个） |
| 连续（信号，N） | 连续 N 天满足 | 连续涨停 |
| 内置 | 逻辑特殊，留在代码里 | 涨停、跌停、炸板、向上跳空、长下影线；大阳线也可改用「比较」表达 |

约 18 个能直接写成规则，其余保留内置。对外结构统一，前端不用区分。

迁移要求：

- 现有 25 个信号改用规则实现后，计算结果必须和现在逐位一致。
- 交叉判定沿用 `ma::cross_signals` 的容差规则，加单元测试对比新旧结果。
- `SignalId` 的序列化名出现在已保存的策略 JSON 里，不能改。

信号目录做成独立页面，用表格展示：名称、分组、偏多 / 偏空、事件 / 状态、定义（自动生成，例如「5 日均线 上穿 20 日均线」）、用到的指标（可点击跳转）、参数、说明。详情页包含：

- 今天哪些股票出现了（已有功能）
- 在某只股票 K 线上的触发点
- 被哪些策略使用
- 历史表现：触发后 5、10、20 日的收益（之前方案规划过，属于后续阶段）

自定义信号（后续阶段）：新增 `app.signal` 表。内置信号只读，可以「复制一份再改」。策略引用信号 ID，改了自定义信号会影响引用它的策略，页面上要提示。

### 5.4 策略层：明确买点和卖点

`Definition` 的结构基本保留。要改的是：

- 展示：策略页分成「股票池」「买入规则」「卖出规则」「排序」四块，每条规则链接到对应的信号或指标。
- 巡检输出三类结果（按 D5 的单只股票状态机）：
  - 今日买点：今天从空仓变成持有
  - 今日卖点：今天触发卖出规则，带上原因（例如「跌破 20 日均线」「亏损 8% 止损」）
  - 持有中：已经持有几天、浮动涨跌多少
- 个股页可以选一个策略，在 K 线上标出历次买点和卖点，数据和单只股票回测同源。
- 巡检、个股页、单只股票回测共用同一个状态机，规则不能各写一套。

### 5.5 诊断：接入同一条链路

把四个维度的判断改成「指标 + 阈值」或信号，卡片上显示依据（例如「依据：5、20、60 日均线多头排列」），并链接到对应条目。

### 5.6 页面结构

现在的「说明」页拆成目录页：

```
数据   →  指标   →  信号   →  策略
目录      目录      目录      列表 / 详情（买点、卖点、持有中、回测）
详情      详情      详情      编辑器
```

每个详情页都有「从哪来」和「被谁用」两个区块。后端新增关系接口，从指标、信号、策略的定义中推算引用关系。现有链接 `/guide#sig-{id}`、`/guide?tab=indicators#ind-{id}` 要保留跳转，`router.tsx` 里已有处理旧地址的先例。

## 6. 分阶段

| 阶段 | 内容 | 范围 |
| --- | --- | --- |
| 1 | 数据、指标、信号、策略目录页，加「从哪来 / 被谁用」关系；补充指标元数据（输入、固定参数、常用阈值、示例） | 后端加元数据和关系接口，前端为主，不改计算逻辑 |
| 2 | 信号改成规则定义，内置信号迁移，结果逐位一致 | 重构 `signals.rs` 并补测试；写新 ADR |
| 3 | 自定义信号：`app.signal` 表、增删改接口、编辑器 | 前后端，新增迁移 |
| 4 | 策略买卖点：巡检输出今日买点、卖点、持有中；K 线上标出买卖点 | 后端巡检加新表（新增迁移），前端策略页和个股页 |
| 5 | 接入估值等非行情数据 | 已搁置（D8） |
| 6 | 信号历史表现统计 | 计算量大，可能要物化 `mkt.signal_event`，见之前方案第 6.3、6.4 节 |

建议从阶段 1 开始：不改计算逻辑，风险最低，也能直接解决「不知道有什么、不知道怎么用」的问题。

## 7. 和现有决策的冲突

`docs/decisions/strategy_design.md` 第 3 条：「指标和信号用代码中的固定目录……用户只能选择和调参数，不能自定义公式。」阶段 2、3 会推翻这一条，届时要新写 ADR，并把旧决策标为部分取代（`superseded`）。新方案用的是固定几种规则类型，不是任意表达式，是对旧 ADR 中「用配置表达就要发明一套表达式语言」这个顾虑的折中。

## 8. 未确定事项（开始对应阶段前要问用户）

1. 自定义信号只用固定的几种规则类型（建议），还是允许写表达式？（影响阶段 2、3）
2. 股票已在持有中又出现买点怎么处理？建议忽略，等卖出后再看新的买点，和现有单只股票回测一致。（影响阶段 4，未确认）
3. 阶段 4 的买入价按次日开盘价还是当天收盘价？现有回测是次日开盘成交，建议保持一致。（未确认）
4. 从哪个阶段开始？建议阶段 1，未确认。
5. 阶段 1 的数据目录范围：只展示日线和复权，还是列出全部数据集？
